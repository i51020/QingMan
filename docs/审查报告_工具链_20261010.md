## 三、P1 问题（建议本阶段修复）

### P1-1｜`store.py` MANIFEST 落盘为 CRLF（唯一漏写 `newline="\n"` 的写盘点）

- **位置**：`tools/store.py:229-231`
  ```python
  (dest / filename).write_text(
      json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8"
  )
  ```
- **现象**：`Path.write_text` 默认 `newline=None`，在 Windows 下把 `\n` 译为 `os.linesep`（CRLF）。项目其余**全部**写盘点（`release.py:47`、`promote.py:114`、`handoff.py:188`、`routes.py:169/344/452`）都显式 `newline="\n"` **并留注释解释这个坑**——唯独这里漏了。
- **实证**（两路）：
  1. 盘上现有清单 **29 / 29 份全部含 CR**；
  2. 隔离临时目录跑 `store.do_commit` → MANIFEST **15 个 CR**（571 B）。
- **影响**：违反「§编码基线：文本文件用 LF」；清单字节随平台漂移（Windows 生成 ≠ Linux 生成），与项目反复强调的字节一致性原则相悖。**功能不受影响**（`json.loads` 容忍 CRLF），故不列 P0。
- **守卫盲区**：`verify.py:347-361` 的「换行一致性」守卫只遍历 `root/"src"` + `VERSION` + `start.bat`，**完全不覆盖 `versions/`** —— 全项目 CR 扫描显示 `versions/` 是**唯一**含 CR 的目录，恰在盲区内。
- **建议**：① `store.py` 改为 `with ... .open("w", encoding="utf-8", newline="\n")`；② 换行守卫扩展到 `versions/**/*.json`；③ 历史 29 份是否批量归一为 LF —— **属覆盖操作，需你裁决**（不改也不影响功能）。

### P1-2｜`smoke.py` 复用沙盒时**第二次必然误报 FAIL**

- **位置**：`tools/smoke.py:140-143`（`dryRun` 断言）+ `187-197`（沙盒选择）
- **现象**：`--keep` / `--sandbox` 语义是「复用沙盒」，但脚本**不清**上次的 `生成结果/`；第二次运行时 `dryRun` 断言 `not target.exists()` 恒为 False → 报 FAIL。
- **实证**：同一 `--sandbox` 连跑两次 ——
  - 第 1 次：`[PASS] dryRun → 200 且不写盘` → 17/0
  - 第 2 次：`[FAIL] dryRun → 200 且不写盘  200 created=True` → 16/1
- **对照**：`browser_smoke.py:391-400` **已经修了同类问题**（复用前清自身产物）——两件工具体例不一致。
- **影响**：工具自身**假失败**；`--keep`（文档化用法）第二次起必红，会污染「四件套」结论。
- **建议**：`smoke.py` 复用沙盒前清 `生成结果`（对齐 `browser_smoke.py`）。

### P1-3｜`handoff.py` 实况段**两处渲染失真**（且 verify 自洽检查发现不了）

实况段是接续说明的核心，供新会话/跨平台 AI 无损接手；verify `第 8 项` 用**同一函数**渲染比对，只能证「未过期」，**证不了「内容正确」**。

**P1-3a｜「修订 tag」永远只列 2 个历史残留**
- **位置**：`tools/handoff.py:146,155-156`，过滤模式 `git tag -l "V*-r*"`
- **实证**：`git tag` 实际有 `V0.0.1` ~ `V0.0.25` 等版本 tag；`V*-r*` 只命中 `V0.0.1-r2`、`V0.0.1-r3`。渲染结果 ⇒ `**修订 tag**：V0.0.1-r2 V0.0.1-r3`
- **影响**：接手方会误以为项目最新 tag 停在 `V0.0.1-r3` / 最新版未打 tag。模式停留在已废弃的 `-r` 命名。
- **建议**：渲染改为版本 tag（如「最近 N 个版本 tag」）+ 保留修订 tag 单列；verify 增断言「tag 行必含当前 `VERSION`」。

**P1-3b｜「时间线最新」日期永远显示 `(未标日期)`**
- **位置**：`tools/handoff.py:98`，日期正则 `^###\s+(\d{4}-\d{2}-\d{2})\s*$`
- **实证**：`timeline_latest()` ⇒ `'(未标日期) · 21:28 – 22:05 · V0.0.25 …'`；正则对 `### 2026-10-10（续十五）` 返回 **False**（`（续十五）` 后缀不被 `\s*$` 容忍），对 `### 2026-10-10` 返回 True。
- **影响**：日期字段永久丢失。
- **建议**：正则放宽为 `^###\s+(\d{4}-\d{2}-\d{2})`（允许后缀）；verify 增断言。

### P1-4｜`browser_smoke.py` 全部纯函数**零测试**（守卫的守卫缺位）

- **位置**：`tools/browser_smoke.py` —— `find_browser` / `parse_metrics` / `console_lines` / `as_int` / `verify_metrics`
- **现象**：这 5 个函数是 9 项页面断言的**全部判定逻辑**，但 `tests/` 无任何覆盖；verify 的「浏览器冒烟覆盖 V0.0.25」只做**静态 token 锚定**（防被削成空壳），**不验证判定逻辑本身正确**。
- **风险**：`verify_metrics` 的阈值（`sec_before == sec_en == sec_zh`、`cjk == 0`、`chip == VERSION`）一旦被写坏，静态锚定拦不住。
- **建议**：新增 `tests/test_browser_smoke.py`，对纯函数做单元级固化，尤其 `verify_metrics`：喂「正常指标」应全 PASS，喂「P1-1 回归指标（分节 7→14→21）」应**恰好**该项 FAIL（复刻上一轮反向验证的逻辑，但变成常态单测）。
