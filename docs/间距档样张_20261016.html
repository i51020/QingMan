⑥ 结论与建议（我的判断）

建议：先不做「乙」，也暂不做「甲」；优先做「丙」里那半件"诚实"的事。
  • 乙的问题不是"会变"，是"变了未必更好"：76 处改动里，多数是 6px→4px / 10px→8px / 14px→12px 这类±2px 以内的抖动，收益是"数字更整"， 代价是整套视觉要重新验收（且本项目刚在 V0.0.51 批次做过按钮尺寸的整体上调， 再叠一次尺寸变更会把两批视觉改动搅在一起）。
  • 甲的问题不是"不划算"，是"不解决任何事"：它把 63 个魔数改名成 63 个 token， 视觉零变更、语义零收敛，只为让一条守卫能立起来 —— 而那条守卫本身还要再写一遍、 再反向验证一遍。
  • 真正值得先做的是「丙」里的措辞：L4 现在写的是「禁止裸色值、裸尺寸」， 但"尺寸"里只有字号档落地了。这半个承诺每多挂一天，就多一天"读起来像完成"（§三.81）。 把它据实收窄为「色值与字号」（或显式声明"间距/描边/圆角有意不 token 化， 理由是语义绑定代价 > 收益"），比继续留着待决更诚实。
若你仍想推进「乙」：建议取 2px 网格（34 处、单处最大 1px）， 并在独立批次里做 —— 先出真实皮肤下的对照截图，再由你点选； 守卫（7c-2「组件 CSS 无裸间距」之类）必须在尺度落地之后再补，顺序不可颠倒 （反过来会当场数百条红，然后人会去放宽守卫 —— §P2 第 44 项的原话）。
