## 二、分层与依赖审查

**结论：分层清晰、依赖单向，铁律有守卫兜底。**

- 后端依赖方向 `app → routes → dtree_core → config`，无环；`dtree_core` 不 import HTTP，可被单测直接调用（已实测可用）。
- 前端依赖方向 `main → ui/modules → core/i18n`，`tree-model.js` 纯数据、`api.js` 是唯一网络出口（`grep` 确认其余模块无 `fetch`）。
- 无 `innerHTML` / `eval` / `new Function` / `document.write`（`grep` 全量 JS 确认），DOM 一律 `textContent`，**无 XSS 面**。
- 安全模型三层递进且**全部落在服务端**：① 谁能触发（Host 白名单 + Origin 严格同源 + `X-QingMan` 防护头 + 拒答 CORS 预检）② 能写到哪（`check_target` 四类黑名单）③ 写多少（规模阈值 + 只增不删）。此设计正确，无绕过路径。

## 五、问题清单（分级）

### 🔴 P1-1　帮助页每次切换语言都会重复追加全部分节

- **证据（实测）**：无头 Edge 探针（同源 iframe 载入真实 `help.html`，派发 `qmlocalechange`）

  ```
  BEFORE sec=7 nav=7 | AFTER1 sec=14 nav=14 | AFTER2 sec=21 nav=21
  ```

- **根因**：`src/web/js/help.js` 的 `renderSections()`（第 127–142 行）向 `#helpSections` / `#helpNavList` **只 append、从不清空**；而 `qmlocalechange` 监听（第 173 行）每次都调它。`support.js` 的同名函数有 `host.textContent=''`，`help.js` 漏了。
- **影响**：用户在帮助页改语言（或主界面改语言时帮助页已打开）→ 正文与侧栏目录成倍重复，每次切换再翻一倍。
- **修复**：`renderSections()` 进循环前加 `host.textContent=''; nav.textContent='';`。
- **现存守卫为何漏掉**：`verify.py` 只做静态检查，无浏览器运行时测试。

### 🔴 P1-2　首屏「默认示例」的节点名不随语言（且会被永久落盘）

- **证据（实测）**：沙盒副本 + 无头 Edge，`localStorage.qm.lang='en-US'`、无 `data/editor.json`

  ```
  HTML_LANG=en-US | NAMES=青蔓示例项目/素材/原始素材/已整理/产出/说明.md
  ```

- **根因**：`main.js` 第 169 行 `const rootNode = defaultRoot();` 执行在**模块顶层**，此时 i18n 仍停在出厂默认 `zh-CN`；而应用偏好（`initPrefs()`）在第 861 行才调用。`defaultRoot()` 内的 `t('sample.*')` 因此恒取中文。随后 `restoreDocument()` 发现无文档即 `saveNow()`，把中文名**永久写入** `data/editor.json`。
- **影响**：系统语言为英文的首次运行用户，界面英文、示例树中文，且此后一直是中文（已成用户数据）。
- **修复**：把默认根的构建推迟到 `initPrefs()` 之后（例如首次确认无持久化文档时再 `defaultRoot()`），或在语言切换时若仍是「未编辑的默认树」则重建。

### 🔴 P1-3　体积上限两层不一致：传输层上限远小于内容层上限，相关错误码不可达

- **证据（量化）**：复刻 `toDocumentNode` 形态 + `save_editor` 的 `indent=2` 序列化实测

  | 节点数 | JSON 字节 | 结论 |
  |---|---|---|
  | 500 | 92.9 KB | 通过 |
  | 1000 | 178.3 KB | 通过 |
  | **2000** | **349.1 KB** | **超 256KB 传输上限** |
  | 8000 | 1373.9 KB | 超限 |

  上限对照：`MAX_BODY_BYTES = 262144`(256KB) · `MAX_EDITOR_BYTES = 8388608`(8MB) · `MAX_EDITOR_NODES = 20000` · `TEMPLATE_MAX_BYTES = 2MB` · `MAX_ICON_BYTES = 256KB`

- **根因**：`app.py._read_body()` 对**所有**请求体先在 `MAX_BODY_BYTES`(256KB) 处拒绝并返回 413 `bodyTooLarge`；而 `routes.save_editor()` 的 8MB / `save_template()` 的 2MB 检查在该闸门之后，**永远够不到**。
- **影响**：
  1. `editorTooLarge` / `templateTooLarge` 两个错误码及其双语取词、文档说明成为**死代码**；
  2. `MAX_EDITOR_NODES = 20000` 实际不可达（约 1,900 节点即触顶）；
  3. 用户正常的大目录树保存时会收到**误导性的「请求体过大」**，而非「文档超限」。
  4. 图标同理：`MAX_ICON_BYTES=256KB` 的 base64 载荷约 341KB，先撞 413。
- **修复**：二选一——① 抬高 `QM_MAX_BODY` 到覆盖内容上限（并同步 `docs/项目手册.md` 环境变量表）；② 下调内容层上限与 256KB 对齐，并删除不可达错误码。**无论哪种，两个常量必须建立「传输层 ≥ 内容层」的不变式，并加一条断言守卫。**

### 🟠 P2-6　`start.bat` 逻辑不一致：即使 `py -3` 可用也强制要求 `python` 在 PATH

```bat
set "PY=py -3"
py -3 -V >nul 2>nul || set "PY=python"
python -V >nul 2>nul || goto :nopy        REM ← 无条件检查 python
```

- 只装了 `py` 启动器、PATH 里没有 `python` 的机器会被误报「未检测到 Python 3.8+」而拒绝启动，尽管 `py -3` 可用。
- **修复**：把检查改为针对最终选定的解释器（如 `%PY% -V >nul 2>nul || goto :nopy`），或放进两分支内分别判断。

### 🟡 P2-7　`help.js` 死代码

- `buildSupport()`（第 88–107 行）与 `buildSection()` 中 `section.kind === 'support'` 分支（第 121 行）在 V0.0.18 拆页后已无任何分节使用（`helpSections` 实测仅 `ol/ul/note/about` 四种 kind）。
- **修复**：删除两处，或保留但加注明。

### 🟡 P3-8　`inspector.js` 变量声明位置

- `refs.note.addEventListener('input', …)`（第 20 行）引用了声明在其后的 `let currentId`（第 28 行）。运行期无 TDZ 风险（监听器只在之后触发），但顺序反直觉，易在重构时踩坑。建议把 `let currentId = null;` 上移到监听器之前。

### 🟡 P3-9　启动图标每次开页都重传一次

- `launch-icon.js` 的 `lastUploadedKey` 是模块级变量，页面重载即归零；`initPrefs()` → `applySkin()` 的 `onload` 派发 `qmskinchange` → `ensureLaunchIcon()` 首次必然通过 `key !== ''` 判定 → **每次打开主界面都 POST 一次 `/api/launch-icon` 并写一次磁盘**。
- **影响**：无功能损害，但属不必要的写盘与请求。可改为把上次上传的色值 key 存入 `localStorage` 比对。

### 🟡 P3-10　`canMove` 对「节点不存在」返回 `'root'`

- 语义混淆（不存在的节点被判为「根节点不可移动」），调用方据此提示「根节点不可移动」会误导。建议新增 `'missing'` 返回值。

### 🟡 P3-11　模板覆盖/重命名缺少失败回滚

- `save_template`：旧文件已 `os.replace` 入 `.trash` 后若新文件写失败 → 抛 `templateWriteFailed`，此时该模板**从列表消失**（仅在 `.trash` 里可人工找回）。
- `rename_template`：新文件写成功后若旧文件入回收站失败 → 新旧两份同时存在。
- 影响可接受（有回收站兜底），但建议在文档或返回信息中明示「异常时为半完成态」。

### 🟡 P3-12　代码整洁小项

- `main.js` 对 `./ui/inspector.js` 有**两条** import 语句（第 23、28 行），应合并。
- `main.js` 第 787 行 `async function applyTemplate` 行首多一个空格。

### 🟡 P3-13　`build_tree` 对「同名但类型相反」的处理不对称

- 树要求建**目录**、磁盘同名项是**文件** → 报错 `pathConflict`（正确）；
- 树要求建**文件**、磁盘同名项是**目录** → `target.exists()` 为真即计入 `existed` 并跳过（静默）。
- 建议统一为报错或至少在响应里区分说明。

## 六、测试与守卫盲区（本次发现）

| 盲区 | 说明 | 本次如何暴露 |
|---|---|---|
| 浏览器运行时行为无自动化 | `verify.py` 全静态；120 条单测只覆盖 Python 侧 | P1-1 / P1-2 靠临时同源探针才发现 |

**建议新增守卫（低成本、可静态实现）**：
1. `QM_MAX_BODY >= max(MAX_EDITOR_BYTES, TEMPLATE_MAX_BYTES)` 断言（P1-3 防回归）；
2. `schema.json version == VERSION` 断言（P2-4 防回归）；
3. `help.js` 的 `renderSections` 必须含清空语句（AST 定位函数体，P1-1 防回归）；
4. 一条无头浏览器的**冒烟级**页面测试（至少覆盖「载入 index.html / help.html 无 console.error、语言切换后 DOM 计数不变」）。

## 七、总体评价

**架构层面：合格且优于同类本地工具。** 分层铁律明确、依赖单向、契约单点、安全模型三层齐备且全在服务端，工具链（内容寻址存储 + 74 项静态守卫 + 120 单测 + 17 冒烟）在个人项目中属高水位。

**逻辑层面：3 处真实缺陷。** 其中 P1-1（重复渲染）与 P1-2（默认示例语言）是**纯前端时序/清空遗漏**，不影响数据安全；P1-3（上限不一致）是**跨层常量缺乏不变式**，会误导用户且使两个错误码成为死代码。三者均未被现有守卫覆盖。

**一致性层面：文档与契约已明显落后于代码**（P2-4 / P2-5），建议在下一版一并收口——这类漂移不修，会持续削弱「文档即索引」的约定价值。
