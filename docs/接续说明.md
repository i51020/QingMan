### 1.1 两处项目目录：关系与版本差异（**先读这段再动手**）

本机存在**两份** QingMan 工作树。它们**不是副本关系**，而是**时间线上的一前一后**：

| | **DSH 工作区（主线）** | **旧存档（只读）** |
|---|---|---|
| 路径 | `D:\Data\deepseek-harness\default-workspace\QingMan` | `D:\Data\WorkBuddy\2026-10-09-12-26-55\QingMan` |
| 版本 | **以 `VERSION` 为准（现 V0.4.5）** | V0.3.12（定格，不再更新） |
| git HEAD | `8e4f7fb` | `466df19` |
| 含 V0.4.0 的 `skipped` 实现 | ✅ 有 | ❌ 没有 |
| 角色 | **后续开发都在这里** | **历史存档，仅供对照 / 回看** |

**两处的关系**：旧存档是 DSH 接入前的最后一个状态；V0.3.13 与 V0.4.0 的改动**只落在 DSH 工作区**，
从未回写旧存档。因此**旧目录缺少**：在线版导出修复、错误文案占位符修复、模板 `skipped` 清单、
以及全部文档更新。

**为什么会有两份**：DSH 是另一套运行时，其 workspace 被固定在
`D:\Data\deepseek-harness\default-workspace\QingMan`，且**沙箱只允许写该路径**，
无法直接把旧目录当工作区（旧目录对 DSH 是只读的）。

> ⚠ **新 AI 的判断题**：
> - 要**继续开发 / 修 bug / 发版** → 用 **DSH 工作区**（路径见上表第一列）。
> - 要**看 V0.3.12 及之前的历史状态** → 用旧存档，或直接 `git checkout 466df19`。
> - **两份并存时，一律以 DSH 工作区为准**；旧存档里的 `VERSION` 停在 V0.3.12 是**正常现象**，不是故障。
> - 若某天要把成果并回旧目录：以 DSH 工作区的 git 历史为准做同步，**不要反向覆盖**。

**为什么必须有这一段**：项目曾落在 `D:\Data\WorkBuddy\<会话时间戳>\QingMan\`，**目录名含会话时间戳
—— 新会话不会共用该目录**，AI 的默认工作目录会变；会话记忆同样躺在会话目录内，**无法跨会话继承**。
唯一可靠的锚点是**项目内的文件**，因此必须显式给出绝对路径，并说清**哪一份才是最新的**。
（2026-10-21 实测教训：锚点段只写旧路径时，新 AI 会打开 V0.3.12 的副本，当天全部工作都看不到。）

> 若日后项目再次搬迁，改三处：本节代码块内的路径、§1.1 的两处对照表、以及 `docs/项目约定.md` §P1-6 的背景段。

> **⚠ 手上只有「接续包」时，先补一个完整开发包**（V0.3.0 实测）：
> 接续包内只有 `src/` `docs/` `locales/` 与 5 个根文件，**不带 `tools/` `tests/` `templates/` `store/` `versions/`**。
> 解压后 `tools/gate.py`、`tools/verify.py` 都不存在，`unittest discover -s tests` 直接报
> `Start directory is not importable`；`store/` `versions/` 缺失 ⇒ **没有回退点**。
> 也就是说：读代码、改 `src/` 可以，但**改完无法验证、改坏无法回退**。
> 要继续开发并交付，必须用 `py -3 tools/handoff_pack.py --full` 产出的
> `QingMan-完整开发包_<版本>_<日期>.zip`（详见《项目手册》§七.5）。
