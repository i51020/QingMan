# 青蔓 QingMan · 项目手册

更新日期：2026-10-09　|　当前版本：V0.0.6

---

## 一、项目概述

青蔓 QingMan 是一个**本地离线运行的目录结构设计工具**：可视化编辑目录树，一键在磁盘上生成真实目录。

与前代参考项目（E: 盘上的文心助手接续包）的根本区别：**从零重写、按专业架构拆分**，不再使用单文件 HTML。参考项目仅作功能与内容参考，代码不继承。

## 二、命名口径

| 项 | 取值 |
|---|---|
| 中文名 | 青蔓 |
| 英文名 | QingMan |
| 项目根目录名 | `QingMan`（英文，保证命令行与脚本兼容） |
| 界面显示 | 中文主标「青蔓」+ 英文副标「QingMan」 |
| 后端包名 | `server`，启动模块 `server:__main__` |

## 三、技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | 原生 HTML + CSS + ES Module | 零构建、零依赖、离线可用，改动即生效 |
| 后端 | Python 标准库（`http.server`） | 零第三方依赖；沿用参考项目路径，环境已具备 |
| 通信 | HTTP + JSON，仅监听 `127.0.0.1` | 本地单机，无跨域与网络暴露问题 |
| 运行环境 | Windows 10/11 + Python 3.8+ | 完全离线 |

│  │  ├─ base.css          基础元素：按钮、输入、chip、提示 + 品牌区（主界面与帮助页共用）

│  └─ js/
│     ├─ main.js           主界面装配层：状态 → 视图 → 交互绑定 → 编辑态自动保存 → 自检；含生成参数区折叠态（`qm.genBar`）

│     │  ├─ bus.js         事件总线（发布/订阅）
│     │  ├─ store.js       状态仓库（唯一状态源）
│     │  └─ api.js         后端调用唯一入口（其余模块禁用 fetch）
│     ├─ modules/
│     │  └─ tree-model.js  数据模型：增删改查 / 统计 / id 唯一性 / 文档序列化。纯数据，不碰 DOM 与网络
│     └─ ui/
│        ├─ tree-view.js   目录树渲染与交互（折叠态只存视图层）

│  ├─ dtree_core.py        纯逻辑：校验 / 统计 / 落盘 / 编辑态文档校验，不依赖 HTTP

│  └─ app.py               HTTP 层：端口扫描、静态服务、分发、开浏览器

data/                     运行时数据（**项目根**，不在 src/ 内）

**分层铁律**

1. `tree-model.js` 不碰 DOM、不碰网络。
2. `tree-view.js` 只渲染、只回传事件，不改数据。
3. 所有网络请求必须走 `core/api.js`。
4. `dtree_core.py` 不 import HTTP 相关模块，可被 CLI/测试直接调用。
5. 路径与端口只在 `config.py` 定义，其余模块不得自行拼接。
6. **所有面向用户的文案只写 `js/i18n/zh-CN.js`**：页面只留 `data-i18n*` 键名，JS 只调 `t(key)`。**除 `i18n/` 目录外，任何文件不得出现中文字符串字面量**。`verify.py` 有「主界面无硬编码中文」「帮助页无硬编码中文」「JS 文案经取词表 §P0-3 L1」三项把关（§P0-3 L1/L2）。
7. **颜色只在 `css/tokens.css` 写死**：组件样式一律 `var(--qm-*)`；皮肤通过覆盖变量实现，**组件不得出现 `.skin-*` 选择器**。`verify.py` 有「组件 CSS 无裸色值」「组件 CSS 不感知皮肤」两项把关（§P0-3 L4/L5）。
8. **编辑态文档的校验只在服务端定论**：前端 `fromDocumentNode()` 做容错转换，服务端 `dtree_core.validate_document()` 做严格判定。**不得只靠前端把关**（§P0-7 E3）。
9. **写盘目标只由 `dtree_core.check_target()` 放行**：任何落盘路径必须先过 `config` 的盘根/系统目录/用户目录/项目自身四类黑名单与规模阈值。**前端校验不能替代它**（§P0-1，见 §八）。
10. **新增偏好键必须声明在 `js/i18n/index.js`**（导出常量），**不得**把 `'qm.xxx'` 这类点分字面量写进别的模块 —— 「取词键闭包」检查把 JS 里**任何** `a.b` 形式的字符串字面量都当作取词键，而 `i18n/` 目录被该检查排除。当前三键：`qm.lang` / `qm.skin` / `qm.genBar`（§P0-3 L6）。
11. **折叠态类状态只在启动时定一次并落盘**，不要在渲染时"动态推断"：生成参数区若按"目标位置是否已填"推断，用户输入第一个字符就会自动收起（V0.0.6 实测教训，见 §`README.md` 中栏一节）。

**帮助页与主界面的关系**：独立页面，由主界面顶栏「帮助」按钮以**新标签**打开 —— 主界面内存里可能正握着一棵尚未落盘的目录树，同标签跳转会丢掉编辑态。

## 五、接口约定

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 返回 `{ok, app, nameZh, version}` |
| POST | `/api/generate` | 生成目录。请求体见 `src/shared/schema.json` 的 `generateRequest` |
| GET | `/api/editor` | 读取编辑态文档。`doc` 为 `null` 表示尚无文档；文档损坏返回 400 `editorCorrupt` |
| PUT | `/api/editor` | 保存编辑态文档（**写操作，需防护头 `X-QingMan`**）。服务端重新校验，不合法拒写 |
| GET | `/*` | 静态文件服务，根目录为 `src/web/`，带路径穿越防护 |

`/api/generate` 请求体：

```json
{ "target": "E:\\我的项目", "root": "可选根文件夹名", "dryRun": true, "tree": { "目录": {} } }
```

树结构规则：值为 `{}` 对象 → 目录；值为字符串 → 文件（字符串即文件内容）。

`/api/generate` 响应（含 P0-1 回填的规范化目标路径）：

```json
{ "ok": true, "target": "E:\\我的项目", "root": "我的项目", "dryRun": false,
  "plannedDirs": 3, "plannedFiles": 1,
  "createdDirs": ["…"], "createdFiles": ["…"], "existed": ["…"] }
```

**写盘目标的四项前置判定**（§P0-1，全部服务端）：路径规范化（R1）、盘根（R2）、系统/用户/项目目录黑名单（R3–R5）、规模阈值（R6）。任一项不通过即返回 `400` + 明确错误码：`targetInvalid` / `targetTooShallow` / `targetBlocked` / `targetReserved` / `tooManyNodes`。**`dryRun` 不豁免 R6**（上限针对"计划规模"本身）。

**生成文件的换行固定为 LF**（`open(..., newline="\n")`）：产出**只由输入决定，不由平台决定**。注意 `.bat` / `.cmd` / `.ps1` 是本策略的已知例外（见 `docs/项目约定.md` §P2 第 12 项）。

**`/api/editor` 与 `/api/generate` 是两条独立的路**：前者读写编辑态（含 id），后者只读内存树并写目标目录。`treePayload()` 把内存树转成 `{名称: 内容}` 的落盘载荷（**不含 id**），`toDocumentNode()` 转成含 id 的持久化节点 —— 两者不可混用。

`/api/editor` 请求与响应：

```json
PUT  { "doc": { "schemaVersion": 1, "root": { "id": "d…", "type": "dir", "name": "根", "children": [] } } }
200  { "ok": true, "path": "…/data/editor.json", "savedAt": "2026-10-09T18:24:02+08:00", "bytes": 405, "stats": { "dirs": 1, "files": 1 } }
```

## 七、版本约定与流程（核心）

**SemVer 三段式：`V<MAJOR>.<MINOR>.<PATCH>`，从 V0.0.1 起。** 版本号唯一来源是项目根 `VERSION` 文件。
旧「V0.01 起、每次 +0.01」规则于 2026-10-09 作废。

| 递增 | 语义 | 例子 |
|---|---|---|
| `patch` | 修复、纠错 | V0.0.1 → V0.0.2 |
| `minor` | 新增功能 / 逻辑迭代 | V0.0.2 → V0.1.0 |
| `major` | 不兼容变更 | V0.1.0 → V1.0.0 |

**升版判据**：凡改动 `src/` 或交付契约 → 升版；纯文档、纯工具改动 → **不升版**，只在 `docs/任务进度.md` 记一条时间线。

### 7.1 五步流程

| 步 | 动作 | 命令 | 红线 |
|---|---|---|---|
| 1 | 在预览区开发 | 手动 | 绝不直接在 `src/` 上试错；`preview/` 按需新建，**落地后即清空**（§P1-7） |
| 2 | 交付校验 | `python tools/verify.py preview/V<版本>` | **46 项**校验（主线 **49 项**，带 `--against` 各 +2），不通过不落地；改 `src/` 另跑 `unittest` + `tools/smoke.py`（§P0-2 T5） |
| 3 | 落地主线 | `python tools/promote.py --from preview/V<版本> --force` | 单向：预览 → 主线，只复制不删除。主线非空时必须 `--force` |
| 4 | 提交版本 | `python tools/store.py commit --note "说明"` | 落地后立即执行；写 blob 池 + 清单（同版本则追加修订）。**它打的是「此刻盘上的 `src/`」+「此刻的 `VERSION`」这个组合，两者必须已配套** |
| 5 | 升级版本号 | `python tools/release.py bump --kind patch` | **改主线之前必须先 commit**；不升版则跳过本步，由 §P0-6 修订机制留回退点 |

> `--from` 缺省时按主线 `VERSION` 推导为 `preview/<当前版本>`，工具内不写死任何旧编号。
>
> **⚠️ 提前 `bump` 的陷阱**：若先把 `VERSION` 升到新版却**尚未落地**，此时执行 `release.py snapshot`（= `store.py commit`）会把**上一版的代码**装进**新版本的清单**。落地前请用 `verify.py . --against <上一版>` 确认主线仍等于上一版基线。详见 `docs/错误笔记.md` §三.18。

### 7.2 存储机制：内容寻址（借鉴 Git）

```
store/objects/<sha256前2位>/<sha256>      blob 池：路径即内容的指纹，相同内容只存一份
versions/<版本>/MANIFEST.json             版本基线（修订 r1）：路径 → 指纹 + 元数据
versions/<版本>/MANIFEST-r<N>.json        同版本后续修订（r2、r3…），不升版时留回退点
```

**修订引用语法**：`V0.0.1`（= 该版本最高修订）／`V0.0.1@r1`（基线）／`V0.0.1@r2`（第 2 次修订）。

`MANIFEST.json` 字段：

| 字段 | 说明 |
|---|---|
| `version` | 版本号，必须与目录名一致（`verify.py` 会校验「清单自洽」） |
| `revision` | 修订号；r1 为基线，r2 起为同版本追加修订（旧清单无此字段，按文件名补足） |
| `createdAt` | 提交时间 |
| `parent` | 上一**版本**，构成跨版本链 |
| `parentManifest` | 同一版本内的上一清单文件名，构成**修订链**（r1 为 `null`） |
| `note` | 提交说明 |
| `legacyAlias` | 旧编号别名（如 V0.0.1 的 `V0.01`） |
| `fileCount` / `files` | 文件数 ／「路径 → `sha256:` 指纹」映射 |
| `digest` | 清单摘要：对「路径 + 指纹」按路径排序后整体求 SHA-256（**改名也能检出**） |

命令一览：

| 命令 | 作用 |
|---|---|
| `python tools/store.py commit --note "说明"` | 提交当前 `src/` 状态；同版本已有清单时**追加修订**而非跳过 |
| `python tools/store.py checkout <版本[@rN]>` | 回退到指定版本／修订 |
| `python tools/store.py log` | 列出版本链（同一版本内按修订倒序） |
| `python tools/store.py diff <版本[@rN]> <版本[@rN]>` | 输出 改动 / 新增 / 缺失 |
| `python tools/store.py fsck` | 校验 blob 池完整性（文件名 == 内容指纹） |

**实测去重效果**：V0.0.1 → V0.0.2 的 23 个文件只新增 3 个 blob、复用 20 个（对象池 22→25，而非 45）。

### 7.3 版本隔离

- `preview/V<版本>/` —— 试运行区，完整可独立启动，与主线物理隔离。测试污染只可能发生在这一层。**平时只留 `README.md` 占位**（生命周期规则见 §P1-7：只服务单次开发、`promote` 后即清空、不归档 `legacy/`、目录保留在 git 跟踪内）。需要试跑时才按版本新建（旧编号 `preview/V0.01/` 已于 2026-10-09 整体归档至 `legacy/preview-20261009/`）。
- `versions/V<版本>/MANIFEST*.json` —— 版本清单，**只增不改**。基线为 `MANIFEST.json`（r1），同版本后续改动追加为 `MANIFEST-r<N>.json`，**任何已有清单都不覆盖**（规则见 `docs/项目约定.md` §P0-6）。
- `store/objects/` —— blob 池，**只增不改**；同一内容永远不会写第二份。
- 纳入版本控制的文件：`src/` + `start.bat` + `VERSION`。`tools/` `templates/` `docs/` 为项目级资产，不进版本清单。
- 旧编号快照 `versions/V0.01/`（含 `SNAPSHOT.json`，MD5 口径）**已于 2026-10-09 清理**。它实为**孤儿目录** —— 无 `MANIFEST.json`，`store.py` 的 `list_versions` 本就不把它视作版本。清理前已核验：其 22 项中 **21 项与 `V0.0.1` r1 清单逐字节相同**（唯一差异是 `VERSION` 内容 `V0.01` vs `V0.0.1`，属编号重制的必然差异），**内容完全可再生**，故按 §P1-4/§P1-7 原则**不归档 `legacy/`**，直接 `git rm`（回退锚点见 `docs/任务进度.md`）。

### 7.4 回退

```bash
python tools/store.py checkout V0.0.1        # 按清单从 blob 池重建（取该版本最高修订）
python tools/store.py checkout V0.0.1@r1     # 精确回退到基线修订
python tools/store.py checkout V0.0.1@r3     # 精确回退到第 3 次修订
python tools/verify.py . --against V0.0.1    # 确认与清单完全一致
```

回退时「当前有、目标版本没有」的文件，先复制进 `store/.trash/<时间戳>/` 并**逐字节校验**，通过后才移除原文件 —— 全程不真删，可反复回退。

## 八、安全说明

**三层递进的闸门**（"谁能触发" → "能写到哪" → "写多少"）：

| 层 | 约定 | 内容 |
|---|---|---|
| ① 谁能触发 | §P0-5 | 仅监听 `127.0.0.1`（监听回环 **≠** 只有本机能调用）；`app.py` 统一中间件做 **Host 白名单 + Origin 严格同源（scheme/host/port）+ 写操作防护头 `X-QingMan` + 拒答 CORS 预检** —— 可挡 **DNS rebinding** |
| ② 能写到哪 | §P0-1 | `dtree_core.check_target()`：路径 `resolve()` → 拒盘根（至少两级）→ 拒系统目录**整棵子树**（`SystemRoot`/`System32`/`Program Files`/`Program Files (x86)`/`ProgramData`）→ 拒用户目录**根本身**（`USERPROFILE`/`Desktop`/`Documents`/`Downloads`，**子目录放行**）→ 拒项目自身及其上级 |
| ③ 写多少 / 怎么覆盖 | §P0-1 R6–R8 | 节点总数超 `QM_MAX_NODES`（默认 500）**服务端直接拒绝**；目录已存在 → **复用**，文件已存在 → **跳过不覆盖**；**全程永不删除** |

**其余既有防护**

- 不收集任何用户数据、不上传任何信息
- 静态服务做路径穿越防护（`resolve()` 后校验是否仍在 `web/` 内）
- 目录名校验：非法字符 `\ / : * ? " < > |`、控制字符、`.` `..`、Windows 系统保留名
- 请求体大小上限保护（`QM_MAX_BODY`）
- 生成操作需用户在前端主动点击

**为什么边界必须在服务端**：前端弹窗与校验属 UI 层、可绕过 —— 任何本地网页（乃至经 DNS rebinding 的公网页面）都能直接 `POST /api/generate`。因此 §P0-1 的判定全部落在 `config.py` + `dtree_core.py`，命中黑名单返回 **4xx + 明确错误码**（`targetTooShallow` / `targetBlocked` / `targetReserved` / `tooManyNodes`），**不是 500**。

**验收**：`tests/test_dtree_core.py`（R1–R8）+ `tests/test_routes.py` + `tools/smoke.py` 三项边界用例与「超限未落盘」断言。
