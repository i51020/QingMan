## 一、流程纪律（最高优先级，违反即返工）

**问题**：口头声称"已完成/已修复"，实际未真实写入磁盘。
**整改**：任何交付前必须 `ls -l` 确认真实存在；必须跑语法/完整性校验；没有校验过的文件一律不说"已完成"。

### 2. 未先确认就改 UI

**问题**：用户要求"修改前问我"，却擅自改动样式。
**整改**：UI/风格/布局类改动必须先给出具体方案（改哪个元素 → 改成什么样 → 影响范围），用户明确回复「执行」后才动手。

### 3. 越权改动

**问题**：要求"只改布局"，却顺手新增功能或改逻辑。
**整改**：改布局只动 CSS/DOM 顺序；改 BUG 只修对应问题；不"顺便"重构。

### 4. 测试污染主线

**整改**：一切试错只在 `preview/V<版本>/` 内进行（按需新建，平时该目录为空）。落地主线前必须校验通过；落地后立即 `python tools/store.py commit` 留回退点。

## 二、版本与备份纪律

1. 改主线之前必须先 `python tools/store.py commit --note "说明"`，否则该版本无回退点。
2. `versions/` 下的版本清单与 `store/objects/` 下的 blob **只增不改**，已存在的禁止覆盖。
3. 版本号采用 **SemVer 三段式**（`V<MAJOR>.<MINOR>.<PATCH>`，从 V0.0.1 起）：`patch` 修复 ／ `minor` 逻辑迭代 ／ `major` 不兼容变更。版本号只在 `VERSION` 文件维护，不在代码里硬编码。
4. **升版判据**：凡改动 `src/` 或交付契约 → 升版；纯文档、纯工具改动 → **不升版**，只在 `docs/任务进度.md` 记一条时间线。
5. 全程只复制、不删除。`checkout` 回退时「当前有、目标版本没有」的文件，先复制进 `store/.trash/<时间戳>/` 并逐字节校验，通过后才移除原文件。

## 三、技术坑点（本项目已实测）

### 1. 嵌套错误码占位符未二次填充

**现象**：报错文案出现字面量，如 `「bad/name」不是合法目录名（目录名含非法字符：{name}）`。
**根因**：`segmentInvalid` 模板里嵌了 `{reason}`，而 `reason` 自身又是含 `{name}` 的模板；只做了一层 `format`。
**修正**：内层模板格式化时必须把 `name` 一并传入 —— `message(reason, name=name)`。
**位置**：`src/server/dtree_core.py` 的 `build_tree`、`src/server/routes.py` 的 `generate`。
**状态**：V0.01 已修复，冒烟测试复测通过。

### 2. `__pycache__` 污染

**现象**：跑过校验或启动过后端后，`src/server/` 下会生成 `__pycache__`。

**根因（2026-10-09 已修）**：`tools/verify.py` 第 6 项用 `python -m py_compile` 做语法检查，**校验动作本身会写盘**。后果是「校验 → 目录被污染 → 未动文件 MD5 与快照不一致」，即检查清单里"未动文件与基线一致"这一项永远无法通过 —— 校验工具污染了自己的检查对象。

**修正**：改用 `ast.parse()` 只读解析，校验不再产生任何文件。
**位置**：`tools/verify.py` 第 6 项检查（含 `import ast` 与模块 docstring）。
**复验**：连跑两次校验，缓存残留 **0**；`src` 与 `versions/V0.01/src` 聚合 MD5 恢复一致（`95b157a1e40df6e39c4e7b5b202b7fc9`）；29 项仍全部通过。

**仍适用**：启动过后端进程仍会由 CPython 导入行为生成 `__pycache__`，运行后需清理。
**清理命令**：`find . -type d -name "__pycache__" -exec rm -rf {} +`
**兜底**：`release.py` 与 `promote.py` 均已忽略 `__pycache__` 与 `*.pyc`。

### 3. 后台服务测试后必须显式收尾

**规范**：服务必须以后台方式启动；测完必须按端口定位并停止进程，同时清理测试产物目录。
**定位命令**：`netstat -ano | grep LISTENING | grep ":8791"` → `taskkill //PID <PID> //F`。

### 4. Windows 路径引号

**规范**：`start.bat` 中一律使用 `"%~dp0"` 结尾带反斜杠的形式并用双引号包裹全部路径变量；避免裸路径拼接导致空格截断。

### 5. 静态文件的路径穿越

**规范**：拼接用户可控路径后必须 `resolve()` 并校验仍在 `web/` 内，否则返回 403。禁止直接 `web_root / url_path` 就开读。

### 6. 文件转义规则差异

- HTML 属性里 `\` 是普通字符，不需要转义。
- JS 字符串里 `\` 必须写 `\\`。
- 不要把 JS 转义规则套到 HTML 属性上，会出现双反斜杠。

### 7. 「承诺了却没实现」的检查项

**现象**：`verify.py` 里定义了 `md5()` 函数却**从未被调用**；而本笔记的交付清单写着「未动文件与快照/基线 MD5 一致」，29 项校验里**根本没有这一项**。
**根因**：规则先写进文档，实现没跟上，且缺少「检查项清单 ↔ 代码」的对齐机制。
**修正**：`verify.py` 新增 `--against <版本>` 指纹比对（SHA-256），删除该死代码；校验项 29 → **31 项**。
**教训**：**文档里承诺的每一条检查项，都必须在工具里找到对应实现**；反之，工具做的每一项检查，也应能在文档里找到出处。

### 8. 聚合校验丢失路径

**现象**：`find src -type f | xargs md5sum | awk '{print $1}' | md5sum` 这类写法只对**哈希序列**取摘要，路径不参与运算。
**后果**：文件**改名但内容不变**时，检测不出差异（曾据此误报「三份代码完全一致」）。
**修正**：清单摘要改为对「相对路径 + 指纹」按路径排序后整体求 SHA-256 —— 见 `store.py` 的 `manifest_digest`。

### 9. MD5 的适用边界

**结论**：MD5 密码学上已不推荐（碰撞可行），且多算法混用会造成口径不一。
**规范**：项目内统一使用 **SHA-256** 作为内容指纹（`store.py` / `verify.py` / `MANIFEST.json`）。历史遗留的 `SNAPSHOT.json`（MD5）保留原样，不再扩展。

### 10. 测试失败要先分清「产品缺陷」还是「测试缺陷」

**现象**：N1 冒烟首跑 21/23，两条 FAIL 的**性质完全不同**：

| FAIL | 真实性质 | 处置 |
|---|---|---|
| `Origin: https://127.0.0.1:8795` 被**放行** | **产品缺陷** —— `_guard()` 只校验 Origin 的 host，未校验 scheme 与端口 | 收紧产品：要求 scheme=`http`、host 白名单、port=实际绑定端口 |
| 落盘目录被报"缺失" | **测试缺陷** —— 断言用 `TARGET.rglob()` 拿到的是**绝对路径**，却与相对路径期望值比较 | 修测试：改用 `p.relative_to(SANDBOX).as_posix()` 作基准 |

**教训**：看到 FAIL 先判断"**是产品错了，还是测试错了**"。一律改产品会把正确的实现改坏；一律改测试会放过真缺陷。两条都要留证据（用了哪组输入、期望什么、实际什么）。

**再犯一次（2026-10-09，P0-1 写 `tests/test_dtree_core.py`）**：新写的两条断言一跑就红 ——

| FAIL | 真实性质 | 处置 |
|---|---|---|
| `count_tree({a:{b:{},c:{d:{}}},e.md,f.txt})` 期望 `(3,2)`、实得 `(4,2)` | **测试缺陷** —— 漏数了 `a` 本身（`a`、`a/b`、`a/c`、`a/c/d` 共 4 个目录） | 改期望为 `(4,2)` |
| `dry_run=True` 时期望 `createdDirs == []`、实得计划项 | **测试缺陷** —— 既有契约规定 dryRun **同样返回 planned 结构**（前端要用它显示"演练完成：目录 N"） | 改期望为「只断言 `createdDirs` 长度 == 目录数」 |

**补充判据**：写断言前**先读实现的既有契约**（含函数的返回约定），不要凭函数名推断语义。"我以为是空"不等于"契约是空"。

### 11. 监听回环 ≠ 只有本机能调用

**现象**：服务绑定 `127.0.0.1` 即被视为"安全"，但实测（2026-10-09）`app.py` **全文无任何来源校验**，`do_POST` 仅比对路径。
**后果**：本地任意网页、乃至公网页面经 **DNS rebinding**，都可盲发 `POST /api/generate` 触发磁盘写入。关键认知 —— **CORS 只限制「跨域读取响应」，无法阻止「跨域发起请求」**（简单请求不预检，读不到响应但副作用已发生）。
**规范**：见 `docs/项目约定.md` §P0-5 —— Host 白名单 + Origin 严格同源（scheme/host/port）+ 写操作防护头 `X-QingMan` + 拒答 CORS 预检。
**验证**：沙盒冒烟 25 项，其中「被拒请求均未落盘」单独断言。

### 12. 无头截图必须等样式应用完成

**现象**（2026-10-09，V0.0.3）：用无头 Edge `--screenshot` 验证深色主题，首轮图片显示「背景仍是浅色」，据此一度怀疑 CSS `mask` 或主题变量没生效。

**真相**：页面本身完全正确 —— 探针页读 `getComputedStyle` 得到 `body.background: rgb(22, 26, 31)`、`logo.background: rgb(125, 214, 176)`、`mask-image` 指向 `assets/logo.svg`，全部符合预期。问题出在**抓帧时机**：未加 `--virtual-time-budget` 时，无头浏览器可能在样式完全应用前就截图。

**正确做法**
- 截图命令固定带 `--virtual-time-budget=3000~5000`，并用**独立的 `--user-data-dir`**（避免复用已锁定的 profile 目录而静默失败）
- **判断样式是否正确以计算样式为准**（`getComputedStyle` 探针页），截图只用于确认真实观感
- 探针页模板：加载 CSS 后用 JS 把 `--qm-*` 变量值、`body`/目标元素的 `backgroundColor`、`mask-image`、盒子尺寸打印到页面上再截图 —— 一次拿到全部客观值

**教训**：若按首轮截图下结论，会误判为「mask 方案不可用」并错误回退到内联方案。

### 13. 不可从位图反推矢量源文件结构

**现象**（2026-10-09，V0.0.3 开工前）：仅凭两张 PNG 就断言「`_02_01_01.png` 是源 SVG 的位图导出、`_02_01_02.png` 没有对应 SVG」「SVG 只有 2 个 path、纯黑」。读到源文件后**两处全部推翻**：

- `inkscape:export-filename` 指向的是 **02**，两张 PNG 实为**同一 SVG 的两次导出**
- 源文件实为**两图层三元素**：一个白色圆角底板 `rect` + 一个 `fill:none` 的**不可见** `path`（与可见 path 同形 1748 点）+ 可见 `path`

**规则**：面对设计源文件，**必须逐元素读取实际内容**（图层结构、每个元素的 `style`、`viewBox`、`inkscape:export-*` 元数据），不得从导出物反推。**位图只能证明它自己的像素**。

**附带教训**：源文件里的元素数 ≠ 可见元素数。`fill:none` 且无 `stroke` 的路径是彻底的冗余，直接用于交付会带上无意义的体积与误导性结构。

### 14. `.brand-logo` 依赖父容器为 flex

`.brand-logo` 只声明了 `width` / `height`，**没有声明 `display`** —— 在非 flex 容器中（如普通 `<div>`），它是 inline 元素，宽高不生效，会**塌陷成 0 而完全不可见**。

**实测**（2026-10-09，V0.0.3）：做尺寸可读性对照页时，把标记直接放进普通 `<div>` 做 8 倍放大展示，结果三个放大框**全空**；而同一份 CSS 在页面上方 flex 布局的尺寸行里（`.cell` 为 flex column）显示完全正常。

**约定**：`.brand-logo` 必须在 **flex 容器**内使用 —— 现有两处 `.brand` 均为 `display: flex`，满足前提。若今后要在非 flex 场景复用（如独立图标页、邮件模板），**须先补 `display: block`**；那时属 `src/` 改动，需升版或追加同版本修订。

**推广**：凡只给尺寸、不给 `display` 的组件类，都要写明「依赖 flex 父容器」这个前提。

### 15. `write_text` 的默认换行会因平台改变字节

`Path.write_text(s)` **不传 `newline=`** 时等价于 `newline=None` —— 写出时把 `\n` 统一译为 `os.linesep`。Windows 上 `os.linesep == '\r\n'`，于是**同一段代码在 Windows 与 Linux 会写出不同字节**。

**实测**（2026-10-09，清点 `preview/` 时发现）：

| 写法 | 盘上字节 |
|---|---|
| `p.write_text("V0.0.3" + "\n", encoding="utf-8")` | `b'V0.0.3\r\n'` ← Windows 实际行为 |
| `p.write_text(..., encoding="utf-8", newline="\n")` | `b'V0.0.3\n'` |

**为什么在本项目是硬伤**：项目用 **SHA-256 指纹**校验内容，且 `.gitattributes` 设 `* -text` **禁止任何换行转换**。字节一变指纹即失配 —— `verify.py --against` 会直接判不通过。

**全项目扫描结果**

| 位置 | 判定 |
|---|---|
| `tools/release.py:45` 写 `VERSION` | 🔴 **有害**（bump 后 `VERSION` 变 CRLF） |
| `tools/promote.py:112` 写主线 `VERSION` | 🔴 **有害**（落地后 `VERSION` 变 CRLF） |
| `tools/verify.py:227` 写临时 `.mjs` | ⚪ 无害（临时目录，不落项目） |
| `tools/store.py:229` 写 `MANIFEST.json` | ⚪ 无害（指纹对**文件映射**算，非清单自身字节） |
| `tools/handoff.py:186-188` | ✅ **正确范例**（`open(..., newline="\n")`） |

**易踩的兼容坑**：`write_text` 的 `newline` 参数**Python 3.10 才有**，而本项目下限 **3.8** —— 修法必须走 `open(..., encoding="utf-8", newline="\n")`（`handoff.py` 已这么做，且注释写明原因）。

**另一面（好消息）**：`store.py` 的恢复路径用 `write_bytes`（:196）与 `shutil.copy2`（:308），**逐字节**，故 `checkout` 取回的内容**绝不会被转换** —— 这也是「删掉 `preview/` 仍能完整取回」的技术前提。

**约定**：项目内所有**文本写入**必须显式声明换行，统一 `newline="\n"`；确需 CRLF 的文件（如 `start.bat`）须显式写 `\r\n` 并在约定中单列。

**实例补充（2026-10-09 修复当日）**：`verify.py` 加入「换行一致性」检查后**立即**报出 `src/web/assets/logo.svg` 含 CR —— 它是 V0.0.3 落盘时由**沙盒生成脚本**（同样裸用 `write_text`）产出的。这说明陷阱不只在自己人的工具里，**"临时生成脚本"同样在射程内**。凡生成文本交给项目的脚本，一律照 `newline="\n"` 写。

**尚存同类点（属 `src/` 产品行为）→ 已于 V0.0.4 一并处理（2026-10-09）**

| 位置 | 原状 | 处置 |
|---|---|---|
| `src/server/routes.py:112` 写 `data/editor.json` | 裸 `tmp.open("w")` → Windows 下 CRLF | 改 `open(..., encoding="utf-8", newline="\n")`。该文件不入 git、不进版本清单，此改动**纯为消除平台漂移**，无用户可见影响 |
| `src/server/dtree_core.py:194` 写**生成的目录树文件** | 同上 → **用户产出文件在 Windows 下是 CRLF、在 Linux 下是 LF** | 改 `open(..., encoding="utf-8", newline="\n")` |

**为什么 `dtree_core.py:194` 是「真缺陷」而不只是洁癖**：它写的不是项目自己的文件，而是**用户在磁盘上拿到的产出**。同一棵树在两台不同系统的机器上生成，字节不同 —— 这本身即"不可复现"。修掉之后产出**只由输入决定，不由平台决定**。

**顺带修掉的一个真缺陷**：`routes.py` 的 `save_editor()` 原先返回的 `bytes` 取自**写入前的字符串长度**，而盘上文件在 Windows 下是 CRLF、比它长。响应里的 `bytes` 因此**小于实际文件大小**。改用 `open(..., newline="\n")` 后两者一致，单元测试（`tests/test_routes.py`）专门断言了这一点。

**遗留未决（见 §三.19）**：`newline="\n"` 是**全局**策略 —— 若将来模板里出现 `.bat` / `.cmd` / `.ps1` 节点，LF 会让 `cmd.exe` 的多行解析（`goto` 标签、括号块）出问题。当前 17 套模板的文本文件只有 `说明文档.md`（均 + `.txt` 若干），**尚不触发**。

### 16. `bytes` 字面量只能含 ASCII

**现象**（2026-10-09，P0-2 写 `tools/smoke.py`）：为测「非法 JSON」分支，写了 `b"{不是 json"` → `SyntaxError: bytes can only contain ASCII literal characters`。

**原因**：`b"..."` 是**字节**字面量，源码里只允许 ASCII 字符；中文属非 ASCII，即使在字符串里合法也不能直接写进 `b""`。

**正确写法**：先写 `str` 再编码 —— `"{不是 json".encode("utf-8")`。

**推及**：凡要发非 ASCII 字节（中文请求体、中文文件名）给 `http.client` / `socket` / 文件，一律走 `.encode("utf-8")`。

### 19. 生成文件的换行：全局 LF 与 `.bat` 的边界（遗留未决）

`dtree_core.py` 生成文件时统一用 `newline="\n"`（见 §三.15 修订），这对 `.md` / `.txt` / 无后缀的文本**完全正确**：确定性、跨平台一致、且现代 Windows 编辑器（记事本 Win10 1809+、VS Code）都正常显示。

**但 `.bat` / `.cmd` / `.ps1` 是例外**：`cmd.exe` 对 LF-only 的批处理在**多行结构**（`goto :label`、`( ... )` 括号块、`if ... else` 跨行）下可能解析异常。它们是 **Windows 唯一认可 CRLF 的文本类型**，也正是本项目自身 `.gitattributes` 给 `start.bat` 定 CRLF 的原因。

**当前是否触发**：**否**。17 套模板里的文本节点只有 `说明文档.md`（外加若干 `.txt`），文件名的换行敏感后缀**暂未出现**。但用户在界面上**可以自己新建**名为 `启动.bat` 的节点 —— 那时就是真问题。

**候选方案（未实施，属 `src/` 改动 → 需升版）**：按**扩展名**决定换行 ——

| 扩展名 | 换行 | 依据 |
|---|---|---|
| `.bat` / `.cmd` / `.ps1` | `\r\n` | Windows 唯一认可的批处理换行 |
| 其余（含无后缀） | `\n` | 确定性 + 跨平台一致 |

**关键设计原则**：判据必须是**扩展名**，**不能是 `os.linesep`** —— 后者会把"平台差异"重新引入产出（正是 §三.15 要消灭的东西）。按扩展名是**规则确定**的，同一输入在任何平台产出同一字节。

### 21. `git rm` 会拒绝删除「只有新增暂存」的文件 —— 须 `-f`

**现象**（2026-10-09，清空 `preview/V0.0.6/`）：

```
error: the following files have changes staged in the index:
    preview/V0.0.6/VERSION
    ...（29 个）
(use --cached to keep the file, or -f to force removal)
```

**原因**：这些文件是**新加入索引**（`A`）而**从未提交**；`git rm` 默认拒删"索引与 HEAD 不一致"的条目，属安全护栏。

**git 层面的解法**（仅在"该条目**确已被跟踪 / 已暂存**"时适用）：`git rm -r -f <目录>`。此处的 `-f` **不构成数据丢失风险** —— 内容已由 `store.py commit` 固化在对象池，且主线已是同内容。
> ⚠️ **但"先 `git add` 再 `git rm -r -f`"不是清空 `preview/V<版本>/` 的正确路线** —— 见下方【更正】。

**它牵出的问题（一度以为规则冲突）**：`docs/项目约定.md` §P1-7 的 R1 / R2 / R5 看着打架 —— R1「`promote` 后即清空」、R2「删除统一走 `git rm -r`」、R5「`preview/` 保留在 git 跟踪内」。

**【更正 2026-10-09，沙箱实证】三者从来不冲突 —— 是我把 R2 的适用面放宽了。**

R2 只管「**已被 git 跟踪**的内容」的删除。§P1-7 生效后 preview 副本**本就不该进索引**，于是 R2 对**常态根本不适用**；R1 与 R5 各管自己的事（前者管"何时清"，后者管"目录与占位文件留在跟踪内"）。所谓"三条表面冲突"**是误判**。

**而"先 `git add` 再 `git rm -r -f`"这个处置是错的** —— 我据它写进 §P1-7 的「规则细化」**已作废**。沙箱最小仓库（`_sandbox/gitrm_probe_20261009/`）实证：
1. `git add` → `git rm -r`（无 `-f`）**被拒**（复现本坑）；加 `-f` 后 `git diff --cached` 为空、`git status` 干净 → **净效果为零**：`git add` 除"让 `git rm` 可用"外**毫无作用**。
2. **若 `git add` 后忘了 `git rm` 就直接提交 → `preview/V<版本>/` 真的进入历史**（`git ls-tree -r HEAD` 可见）→ **这套做法会制造它本想避免的结果**（违反 R1 本意）。
3. **正确路线**：**不进索引** —— `git clean -nd preview/V<版本>` 演练 → `git clean -fd preview/V<版本>`；索引不受影响、`git status` 干净，被跟踪的 `preview/README.md` 与目录本身均保留（R5 成立）。

**正确规则（已更正 §P1-7「清空细则」）**：先跑 `git ls-files preview/V<版本>` —— **非空**（副本已被跟踪，历史遗留）→ `git rm -r`；**为空**（从未进索引，§P1-7 生效后的常态）→ **不要 `git add`**，用 `git clean -fd`。两条路都须先备齐三项证据（sha256 逐字节一致 / blob 在对象池 / 可取回）。

**通用教训（已修正）**：遇到"规则之间看着打架"，先分辨是**真冲突**，还是**自己把某条规则的适用面放宽了**。本例属后者 —— 我把 R2 当成了"一切删除都必须走 `git rm`"。**先核准适用面，再谈操作顺序。**

### 23. 「记忆型」UI 状态不能按"用户正在编辑的字段"动态推断

**现象（设计阶段拦下，未上线）**：生成参数区要可折叠。最自然的写法是**不存偏好**，每次渲染时推断：

```js
function genBarCollapsed() {
  return !!el('inTarget').value.trim();   // 目标位置已填 → 收起
}
```

**后果**：用户在展开状态下**输入目标位置的第一个字符**，`input` 事件触发重绘 → 判定瞬间变为"已填" → **参数区自动收起**，把用户正在操作的输入框藏起来。而帮助页的引导顺序恰恰是"先填目标位置"（`help.quickStart.4`）。

**正解**：**这种"记忆型"状态只在启动时定一次并落盘**，之后完全由用户主动切换控制：

```js
function initGenBar() {
  if (!getGenBarState()) setGenBarState('open');   // 首次展开
  renderGenBar();
}
```

**通用教训**：状态推断的**输入**里，不要包含"用户此刻正在改的那个东西"。判断依据要么取**已提交/已保存**的值，要么**只算一次**。

**已固化为验收**：注入式行为探针把这条写成断言 `输入过程不会自动收起/展开`，以后改动若破坏它会立刻变红。

**现象**（2026-10-09，实施「源码 § 引用可解析」守卫时，**实证抓出**）：首版标签正则是 `§\s*([A-Za-z0-9]+…|[\u4e00-\u9fff]+)`。在沙箱探针（`_sandbox/srcref_probe_20261009/`）里，文档串 `"""沙箱探针 · 源码 § 引用守卫反向验证。` 中的**散文**「§ 引用守卫反向验证」被当成标签 `引用守卫反向验证`，报出**误报**：

**通用教训**：**给"符号 + 标识符"写正则时，先定清楚"什么不算引用"**。符号在自然语言里常有非引用用法（此处 `§` 可作"章节"讲），若不在模式里排除，守卫就会**惩罚正常写作** —— 而一个会误报的守卫，最终结局是被绕过。**排除规则本身也要写进文档**（本轮已写入 `verify.py` 代码注释与 §三.22 的「防复发」段）。

**现象**（2026-10-09，V0.0.7：处理 §P2 第 8 项「快捷键约定」时**自查发现**）：我先给出的裁定建议写着「产品为**全鼠标驱动**、无任何全局键盘监听」。落到盘上一查 —— **`src/web/js/main.js:364-370` 早已有 `Ctrl / Cmd + S` 立即保存**（`keydown` + `preventDefault()` + `saveNow()`）。

真正的问题因此**完全反转**：不是"要不要设快捷键"，而是**键位已经存在、帮助页却没写**
（`help.kbd.pending` = 「功能面尚未稳定，键位约定待定，本表暂留空」）—— 这是**文档与实况不符**，而非"待约定"。

**原因**：我把"帮助页留空占位"当成了"没有键位"的证据。**占位文案描述的是"约定未定"，不等于"功能不存在"**；两者之间没有蕴含关系，我却当成了等价。

**处置**：裁定与实施都按实况重写 —— 帮助页**补登** `Ctrl / Cmd + S`（新增取词键 `help.kbd.save`），`help.kbd.pending` 改为「本版仅设上述一项」。§P2 第 8 项条目内**显式标注「原假设经核查不成立」**。

**通用教训**：**"某功能没被文档描述" ≠ "该功能不存在"**。凡在建议/裁定里写"产品**没有** X"，都必须先跑一次反向检索（`grep` 关键词 / 监听器 / 取词键）**证明其不存在**，而不是用"文档里没提"来推定。本项目的 `verify.py` 只能校验"该有的有没有"，**查不出"我声称没有的其实有"** —— 这类错误只能靠人工核实。

### 28. 判据写进文档却**恒为假**：「看该行首是否带 ✅」

**现象**（2026-10-09，V0.0.7）：上一轮把 §P2 改名时，我写下一条判据「**看该行首是否带 ✅**」。本轮执行时发现它**永远为假** —— §P2 是 Markdown 表格，行首恒为 `| 编号 |`，`✅` 全部落在**第 3 列（说明列）之内**。

**危害**：判据是给人（和后续 AI）看的操作说明。一条恒假的判据会让"已结案 / 待决"的分类**完全无法执行**，而表面上它读起来还挺合理。

**处置**：判据改为「看**说明列开头**是否含 **✅**（已结案）／**⚠️**（挂起）；两者皆无即待决」，并在文档里**保留被更正的原文**（划掉 + 说明为何错），而不是悄悄改掉。

**通用教训**：**写"判据 / 检查动作"时必须当场对着真实数据跑一遍**。本项目 §P2 表当时已有 4 行带 ✅，只要随手点开看一眼就能发现判据不成立 —— "看起来对"和"跑一遍对"之间的差距，正是这类文档型错误的全部来源。**判据也是一种"承诺"，同样要有验收**（呼应 §一.7「无实现、无验收的条目不得写入」）。

**【同轮复发，已实测】**：修正判据后，我**立刻又踩了同一个坑**。按新判据（"看**说明列开头**是否含 ✅ / ⚠️"）逐行核对，15 项里有 **4 项判不出来**：

| 项 | 问题 |
|---|---|
| 第 **12 / 13** 项 | 内容已写明"已实施 / 已修复"，**却忘了加 ✅ 前缀**（格式没跟上结论） |
| 第 **11** 项 | `✅` 写在说明列**中间**（"…**✅ 处置结果（2026-10-09 已完成）**"），不在开头 |
| 第 **15** 项 | 用文字"**已裁定并实施**"**代替了符号**，根本没有 ✅ |

**修正**：统一把 `✅` / `⚠️` / `⏳` 放到**说明列开头**（后接简述）。**修正后核验：13 结案 ／ 1 挂起 ／ 1 待决，15 项全部可判定。**

**延伸教训**：**新定的格式规范，必须立刻回头把已有数据全部套一遍**。否则规范只对"从此往后的新条目"生效，老条目继续不合规，判据照样失效 —— 这与"只给新代码加测试、老代码不管"是同一类问题。

### 29. 同一份数据两种口径：字节求和 137K vs `du` 磁盘块 180K

**现象**（2026-10-09，V0.0.7：为 §P2 第 4 项「体积上限」定基线时发现）：我先前写下的基线是「`src/` 合计 **180 KB**」（取自 `du -sh src/`），而本轮写进 `verify.py` 的体积断言按 `st_size` **求和**算出的是 **137 KB**。两者相差 43K。

**原因**：`du` 报的是**磁盘占用**（按文件系统簇对齐，本项目小文件多，每个文件至少占一簇）；`st_size` 求和报的是**逻辑字节数**。二者对同一目录**都正确**，只是口径不同。

**处置**：文档统一采用**与断言一致的口径**（字节求和 = **137 KB**），并**显式注明** `du` 口径为 180K、差异来自簇对齐 —— 避免下次有人用 `du` 复核时以为断言算错。

**通用教训**：**凡是会被工具复算的数字，文档里必须写明口径**（字节 / 磁盘块、含不含子目录、压缩前 / 后）。写"约 180K"而断言算 137K，会让人怀疑断言本身有 bug，白耗一轮排查。**数字的可复现性，取决于口径是否一起写下来**。

### 30. 「本表暂留空」是一句会被代码沉默推翻的断言 —— 它潜伏了 5 个版本

**现象**（2026-10-09，V0.0.7）：帮助页「快捷键」小节自建立起就写「功能面尚未稳定，键位约定待定，本表暂留空」（`help.kbd.pending`）。而在 §P2 第 8 项收口时核对发现，产品**早就有 `Ctrl / Cmd + S` 立即保存** —— `src/web/js/main.js:365-370`（`keydown` + `preventDefault()` + `saveNow()` 跳过防抖）。

**时间线（git 实测）**：

| 提交 | 内容 | 该文案是否成立 |
|---|---|---|
| `fbea984`（提交序 #8） | 帮助页独立成页，写下「本表暂留空」 | **成立** —— 当时产品确实零快捷键 |
| `27770c3`（#12，V0.0.2） | 加入 `Ctrl / Cmd + S` | **从这一刻起即为假** |
| V0.0.3 / V0.0.4 / V0.0.5 / V0.0.6 | —— | 一直为假，**无人发现** |

**性质**：这不是"写错了"。那句文案在下笔时**准确且合理**，问题在于它是一句**与代码耦合、却无人看守的断言**：只要有人新增一个快捷键，它就自动变假，而**代码侧没有任何东西提醒文档侧**。它潜伏 5 个版本、跨 4 次交付校验都没被抓到。

**为什么必须告知（这不只是"写不写"的取舍）**：`main.js:367` 有 `preventDefault()` —— 该键**抢占了浏览器自带的 Ctrl+S「保存网页」**。用户按下去会被产品接管、不会弹出保存网页对话框。帮助页若仍说"本表暂留空"，用户**永远不知道这个键已被占用**。

**处置**：① 帮助页登记该项（新增取词键 `help.kbd.save`）；② `help.kbd.pending` 语义由"待约定"改为"**本版仅设上述一项**，其余待功能面稳定后统一约定"；③ 新增机器守卫 `verify.py` 第 **7g** 项 —— **源码出现修饰键监听（`ctrlKey` / `metaKey` / `altKey`）时，帮助页键位小节必须登记至少一条具体键位**，只留 `help.kbd.pending` 占位即判不通过。四分支沙箱实证：只留占位 → FAIL（并打印源码命中位置）；补齐登记 → PASS；源码无修饰键监听 → 跳过 PASS；键位小节整段缺失 → FAIL。

**通用教训**：**写进文档的"否定性断言"（"没有 X"、"暂留空"、"待定"）必须有人守**。肯定性断言写错了，使用中迟早暴露；**否定性断言写错了没人会察觉** —— 因为"这里什么都没有"看起来永远正常。给这类断言配一个**机器守卫**（本例：源码有键位 → 文档必须有登记，反向不成立），是唯一可靠的解法（与 §三.27 同源）。

### 31. 守卫的扫描范围与它声称的定义脱节 —— 盲区就是这么来的

**现象**（2026-10-10，`tools/` 逐行审查）：`verify.py` 的「换行一致性」守卫，注释与输出都写明契约是「**其余纳入版本控制的文本文件**用 LF」，实现却只遍历 `src/` + `VERSION` + `start.bat`。全项目 CR 扫描（剔除 `.git` / 二进制）显示：**唯一含 CR 的目录恰是 `versions/`，29 份 `MANIFEST*.json` 无一例外** —— 全部落在不扫描的那一侧，故**长期无人发现**。根因＝`tools/store.py` 的 MANIFEST 写盘点用 `Path.write_text(...)` 漏写 `newline="\n"`（全项目**唯一**漏写点，其余写盘点都显式声明并留了注释）。

**为什么它会潜伏**：三件工具各自都看不出问题 —— ① `store.py` 写得出来、`json.loads` 也读得回（CRLF 不影响 JSON 语义）；② `verify.py` 只扫 `src/`，永远绿；③ 我们**看的是「结论：全部通过」，不是「它扫了哪些文件」**。**守卫的"绿"，只代表它自己那一平方公里没问题。**

**处置**（2026-10-10，不升版）：① `store.py` 补 `newline="\n"`；② 守卫扫描范围扩为**版本控制文本文件全集**（含 `versions/`；排除 `data/` `store/` `.git/` `__pycache__/` `.trash/`；`start.bat` 仍单列要求纯 CRLF）；③ 29 份历史清单 CRLF→LF（逐份断言 `json.loads` 语义不变）。**反向验证**：扩范围后守卫立刻 **FAIL 并精确点名 29 份**；隔离 `do_commit` → MANIFEST **0 CR**。

**通用教训**：**守卫的「契约文字」与「实现范围」必须同源**。写范围要用一句**可判定的定义**（如「纳入版本控制的文本文件」），并让代码**从这一定义派生扫描集**，而不是手写一份「我以为够用」的目录清单 —— 两者一旦分叉，盲区必然出现在**「清单之外、定义之内」**那一块。同源的第二层含义：**范围里每新增一个顶层目录，守卫就得跟着被重审一次**（已写入《项目约定》§编码基线）。

**伴生教训（同日现场演示）**：`handoff` 的实况段把**任何未跟踪文件**都算作「未提交改动」—— 于是**新增一份文档就能让 `verify` 第 8 项转红**，而红项文案写的是「已过期」，指向的完全是另一件事。**规律：写完任何新文件后，先跑 `python tools/handoff.py` 刷新实况段，再看 `verify`**（已写入《接续说明》§3.3 红线）。

**副作用纪律（本次实证）**：`py_compile` 会在项目内写 `__pycache__`（含 CR）→ 污染换行守卫，故语法自检一律用 `ast.parse` / `python -B`。本次归一与实证**全程在隔离临时目录**（`tempfile`）或**只读扫描**中进行，项目内 `data/editor.json` mtime 未变（仍 `20:14`）、无 `__pycache__` 残留。

### 32. 「复用沙盒」的语义没有兑现 —— 同一参数第二次跑就自相矛盾

**现象**（2026-10-10，`tools/` 逐行审查）：`tools/smoke.py` 的 `--keep` / `--sandbox` 参数，文档语义是「**复用沙盒**」，实现却**不清**上次留下的产物。于是同一 `--sandbox` 连跑两次：第 1 次 `17/0`（全过），第 2 次 `16/1` —— 失败项是第 7 项 `dryRun → 200 且不写盘`，因为上次真实落盘建的 `生成结果/` 还在，断言 `not target.exists()` 恒为 False。

**为什么它会潜伏**：① 日常跑从不带 `--sandbox`（默认走 `tempfile.mkdtemp` 新建、测完即清），**每次都命中"干净沙盒"这条路径**；② 唯一会踩到的是「为排查而 `--keep` 复用」—— 那正是最需要工具可信的时刻；③ 失败项文案 `created=True` 看起来像**产品**没做 dryRun，而实际是**工具**自己没清场，**归因会被带偏**。

**根因（体例不一致）**：`tools/browser_smoke.py` **早就修了同类问题** —— 它复用前清 `src` / `templates` / `VERSION` / `data` / `browser-profile`，并在注释里写明「`data/` 必须清，否则『默认示例随语言』假通过」。两件同类工具，**一件清、一件不清**，于是缺陷在"看起来已有先例"的情况下仍然潜伏 —— **先例没有制度化，就等于没有先例**。

**处置**（2026-10-10，不升版）：`smoke.py` 在选定沙盒后、起服务前，按**已知名清单** `("生成结果", "big")` 清残留（对齐 `browser_smoke.py` 写法；**只清已知名，不动沙盒内其它内容**）。**并把它升格为约定**（《项目约定》§P1-4「复用型沙盒工具」行 + §P2 第 17 项）：凡支持「复用同一沙盒」的工具，**运行前必须清掉自己上次留下的产物**，使工具**幂等**（连跑两次结论一致），清理范围**只限已知产物名**。

**验证**：修复前连跑 → `16/1`；修复后连跑 **3 次** → 均 `17/0`（第 2 次起打印「复用沙盒，清理上次产物」）；**边界实验**：预置 `生成结果/` `big/` `keepme.txt` → 运行时清 `生成结果` `big`，`生成结果/` 随真实写盘重建、`big/` 已清且未重建、**`keepme.txt` 幸存**（证明「只清已知名」这条约束真的成立，而非把沙盒整个 `rmtree`）。

**通用教训**：**一个"支持复用"的参数，必须在复用路径上自带清场**，否则它的第二次调用就与自己的语义相矛盾。更普遍地：**同类工具之间的体例必须显式统一并写进约定** —— 只要还有一件工具**没**遵守，那件就是下一次的坑（本例：`smoke` 迟于 `browser_smoke`）。判断方法很简单：**把工具连跑两次，结论不一致的，就是没兑现"复用"语义**。

### 33. 「自洽检查」只能证「没过期」，证不了「内容正确」

**现象**（2026-10-10，`tools/` 逐行审查 §P1-3）：`verify.py` 第 8 项守卫的写法是 —— 用 `handoff.render_live(root)` 现场渲染一遍，再与 `docs/接续说明.md` 里**由同一个函数写入**的实况段比对，相等即 PASS。这个断言**永远不可能发现渲染器本身的错误**：渲染器输出什么，它就比对什么，两边天然一致。于是两处失真长期隐身：

| 分项 | 失真 | 实测 |
|---|---|---|
| P1-3a | `handoff.py` 只执行 `git tag -l "V*-r*"` | 实况段**只列修订 tag** `V0.0.1-r2` / `V0.0.1-r3` —— **24 个版本 tag 全部缺席**，接手方会误判「最新 tag 停在 `V0.0.1-r3`」 |
| P1-3b | 日期正则 `^###\s+(\d{4}-\d{2}-\d{2})\s*$` 要求整行**只有**日期 | 而标题是 `### 2026-10-10（续十五）`（带括号后缀）→ 「时间线最新」日期**恒为 `(未标日期)`** |

**性质**：这是「**用被测者校验被测者**」的经典盲区。第 8 项当时被当作"实况段守卫"写进 §P1-6 H4，看起来已经把接续卡纳入了机器校验 —— 实际上它守的是**新鲜度**（有没有过期），而**正确性**（内容对不对）完全没有守卫。**「有守卫」不等于「守住了要害」**。

**处置**（2026-10-10，不升版）：① `handoff.py` 新增 `split_tags()`，渲染改为**版本 tag 与修订 tag 分列**（版本 tag 列「最近 5 个 + 总数」）；② 日期正则放宽为 `^###\s+(\d{4}-\d{2}-\d{2})`（允许标题后缀）；③ `verify` 增 **8c** 两条**内容断言**（80 → **82**）：**「版本 tag 行必须列出真实版本 tag」**、**「时间线最新必须解析出日期」**。两条断言都作用在**渲染输出**上，因此能推翻渲染器本身。

**一处必须记下的判断失误（险些制造假红）**：审查报告原建议断言「tag 行**必含当前 `VERSION`**」。我照此实现前先推演了发布流 —— `bump → store commit → handoff → git commit+tag`：在 `handoff` 那一刻，**新版本 tag 还没打**（`git tag` 是下一步），硬断言必然在**合法的中间态**报红。故最终实现为「**`VERSION` 已打 tag 时必须出现；否则至少需有一个形态合法的版本 tag**」：既堵住旧缺陷，又不制造假红。**教训：任何断言都要先问「它在流程的哪一步成立」**，别把一个只在"稳态"为真的条件写成"恒真"。

**验证**：整项目副本反向验证 —— 对照组（新实现）两项 **PASS**（`24 个版本 tag，最新 V0.0.25` / `2026-10-10 · 22:16 – 22:20 …`）；注入旧行为后两项**精确 FAIL**（`版本 tag 行漏列当前 V0.0.25` / `日期未解析：(未标日期)`）。

**通用教训**：**凡是「生成—比对」式守卫，都必须额外回答一个反问：生成器错了怎么办？** 若比对的两端来自同一来源，那它只配叫「新鲜度检查」，不能叫「正确性检查」。正确性检查必须引入**独立判据**（本例：① 版本 tag 行必须含形态合法的版本 tag；② 日期行不得出现 `(未标日期)` 这一"解析失败哨兵"）。这与 §三.31「守卫的契约文字与实现范围必须同源」是同一族问题的两个面：**前者问"扫到没有"，后者问"算对没有"**。

### 34. 静态 token 锚定拦得住"削成空壳"，拦不住"逻辑写坏"

**现象**（2026-10-10，`tools/` 逐行审查 §P1-4）：`tools/` 8 个脚本，此前**只有 `store` / `versioning` 有单测**。两个最关键的工具全裸奔：

| 工具 | 承担什么 | 覆盖方式 | 覆盖**不到**什么 |
|---|---|---|---|
| `browser_smoke.py` | 5 个纯函数（`as_int` / `parse_metrics` / `console_lines` / `find_browser` / `verify_metrics`）= **9 项页面断言的判定逻辑本体** | `verify` 的「浏览器冒烟覆盖」项**静态锚定 10 个 token** | 判定**逻辑**对不对 |
| `handoff.py` | 渲染函数 = **接续卡内容的唯一来源** | `verify` 第 8 项的**自洽比对**（§三.33） | 内容**对不对** |

静态锚定的设计初衷是对的（防有人把断言删成空壳），但它守护的是**"这些代码还在不在"**，不是**"这些代码算得对不对"**。举个具体例子：`verify_metrics` 里那行 `check(sec_before > 0 and sec_before == sec_en == sec_zh and nav_before == nav_zh, ...)` —— 只要这行还在，10 个 token 锚定全部通过；但如果有人手滑把 `nav_before == nav_zh` 删掉，**没有任何东西会报警**，而 P1-1 的导航累积就再也抓不到了。

**处置**（2026-10-10，不升版）：新增 `tests/test_browser_smoke.py`（**26 项**）与 `tests/test_handoff.py`（**18 项**），把判定逻辑固化为常态回归网；并把「回归测试网 §P0-2」必需清单补上这两个文件 —— **缺文件即 verify 报红**，防止日后被删。

**关键设计：把「一次性反向验证」变成常态单测。** 上一轮（V0.0.25）为验证 browser_smoke 有效，是**当场**注入缺陷、看它 FAIL，然后撤销 —— 这次验证**用完就没了**，下一个人不会重跑。本轮的写法是把它**写进断言**：

```python
# 喂 P1-1 回归指标（分节 7 → 14 → 21）→ 必须**恰好**这一项 FAIL
self.assertEqual(failed_names(run_metrics(dict(NORMAL, secEn="14", secZh="21"))),
                 ["帮助页·分节渲染幂等"])
```

这条断言同时钉住两件事：① 该缺陷**能被抓到**；② **只**这项被抓到（不多不少，防误报扩散）。

**通用教训**：**"有测试"和"测到了要害"是两回事**。判断一个守卫属于哪一类，只需问：**如果我把它保护的那行逻辑改坏，谁会喊？** 若答案是"没人喊"，那它就不是守卫，只是一块**铭牌**（证明这块代码曾经存在）。工具链与产品代码**同标准** —— `tools/` 里的判定函数和 `src/` 里的业务函数一样，都该有单测。

**副作用纪律（本次实测踩到，当场修）**：`test_handoff.py` 需要在临时目录里 `git init` 建最小仓库来测 tag 渲染。首版用裸 `shutil.rmtree` 清理 —— **Windows 下 `.git/objects` 里的文件是只读的**，`rmtree` 抛 `PermissionError`，于是**每次运行都在 `%TEMP%` 留下一串 `qm_handoff_*` 目录**（实测一次全量跑留 10 个）。修法：先 `os.chmod(p, stat.S_IWRITE)` 把整棵树改回可写，再 `rmtree`。**教训**：凡「测试自己造目录再删」的用例，**必须验一次"跑完真的没残留"**，不能只看 `Ran N tests OK` —— 测试的**清理**和测试的**断言**同样是产物，漏了照样污染环境（与 §三.31 的副作用纪律同源）。已泄漏的 15 个目录已当场清理并复查为空。

### 35. 三处「说得和做的不一样」——文案与实际行为脱节

**现象**（2026-10-10，`tools/` 逐行审查 §P2-1 / §P2-2 / §P2-6）：三处都不影响功能，但**都会误导下一个读它的人**：

| 位置 | 说的 | 做的 | 后果 |
|---|---|---|---|
| `verify.py` 无 node 时 | 「未找到 node，**跳过**（【待核实】）」 | `check(False, ...)` —— **判失败** | 若真在无 node 的机器上跑，输出令人以为"这项没参与校验"，实则是**红项**；反过来说，若有人据此以为"跳过不计数"，就会误判门禁通过 |
| `verify.py` `find_node()` | 回退到"托管目录里的 node" | **硬编码** `versions/22.22.2-6/node.exe` | 托管运行时一升级（目录名变了）即静默失效 —— 本机因 PATH 恰好命中托管 node，**这条回退从未被执行过**，所以谁都没发现 |
| `release.py` `do_bump()` | 「请确认已用 `store.py commit` 留好回退点」 | 打印在**改写 `VERSION` 之后** | 提示到达时，被提醒的那件事**已经发生**："先留回退点"这个动作在时间上已不可能 |

**共同性质**：三处都是**文案/命名/时机与其实际语义不符**，且**功能测试全绿** —— 因为功能是对的。它们的危害不在运行期，而在**下一次有人依赖这段文字做判断时**（第 1 条：误判门禁状态；第 2 条：以为有回退其实没有；第 3 条：以为还来得及）。

**处置**（2026-10-10，不升版，§P2 第 20 项）：

- **P2-1**：**不做「真跳过」，只把文案改准** → 「未找到 node —— JS 语法检查无法执行（本条为必需项）」。理由：JS 语法是交付门禁的一项，**静默少一项会让"覆盖变薄"看起来和"全过"一模一样**（同 §三.33 —— 绿必须可信）。
- **P2-2**：改为扫描托管目录下**全部版本取最新**（`node_version_key()` + `iter_managed_nodes()`）。**关键**：按**数字**比较、不是字典序（字典序会把 `9.x` 排在 `24.x` 之后）；并跳过没有 `node.exe` 的目录（实测本机托管目录里有 `current` / `.locks` 两个"看起来像版本"的名字）。
- **P2-6**：提示前移到写盘**之前**。

**验证**：`PATH=""` + `HOME=<空目录>` 跑 verify → `[FAIL] JS 语法  未找到 node —— JS 语法检查无法执行（本条为必需项）`，全文无「跳过」；伪造 HOME 只放 `24.21.0/node.exe` → `find_node()` 返回该路径，而**旧硬编码路径不存在**（旧实现必然返回死路径）；临时副本实跑 `release.py bump` → 提示行**早于**升级行。三条均已补单测（`tests/test_verify.py` 8 项、`test_versioning.py` +3）。

**通用教训**：**「功能对」不等于「可信」**。审查这类问题时，最有效的问法是**逐句反问**：「这句话说的事，代码真的这么做吗？」「这个提示出现在这个时刻，还来得及吗？」「这个回退路径，最后一次被真正执行是什么时候？」—— 三问分别揪出本例的三条。**尤其注意第二条那类**：一条**从未被走到**的回退分支（本机 PATH 恰好命中，硬编码分支始终没执行），它的正确性**从未被任何一次运行检验过**，是典型的"看起来有、其实没有"。

### 36. 受限环境下的「删除到回收站」——手段受限 + 返回码不可信

**现象**（2026-10-10，清理 `D:\Data\WorkBuddy\_sandbox\` 45 项历史残留）：要把文件**送进回收站**（而非永久删除），三种常规手段里**两种被安全策略直接拦截**：

| 手段 | 结果 |
|---|---|
| `Add-Type -AssemblyName Microsoft.VisualBasic` + `[FileIO.FileSystem]::DeleteDirectory(..., SendToRecycleBin)` | ❌ 拦截（"compiles and loads .NET code at runtime"） |
| `New-Object -ComObject Shell.Application` + `InvokeVerb('delete')` | ❌ 拦截（"COM object instantiation can run arbitrary code"） |
| **`ctypes` 直调 `shell32.SHFileOperationW`（`FO_DELETE` + `FOF_ALLOWUNDO`）** | ✅ 可行 |

**坑 1 · 返回码不可信**：`SHFileOperationW` 对**已经成功送入回收站**的项**经常返回 `res=2`**（`ERROR_FILE_NOT_FOUND` 的码值），实测 20 项里 8 项如此。**若以返回码判成败，会误报一批失败**。**正确判据**：操作后**复核目标是否仍存在**（`os.path.exists`）。这与 §三.17「生成类命令不能只看 exit code，要验产物真实存在」同源、方向相反 —— **删除类命令不能只看返回码，要验目标真的没了**。

**坑 2 · 大目录很慢**：把含数百文件的目录送回收站实测 **约 17–36 s/项**（不是同卷 rename 的直觉速度），45 项累计 **6–7 分钟** —— 会被命令超时**静默截断**（早期一次运行删了 6 项即被截，且 `python` 默认缓冲使日志**全部丢失**，表现为"无输出 + SIGTERM"，易误判成沙盒拦截）。**修法**：`python -u`（逐项 flush）+ 显式增大超时 + 分批。

**坑 3 · `Add-Type` 字面词本身也触发拦截**：连注释或 `Write-Output` 字符串里出现该**字面词**都会命中模式匹配 → 换不含该词的表述。

**通用教训**：**受限环境里「存在标准做法」不等于「这个做法可用」**。落地高风险动作前**先实测探测可用手段**（本例：先 `Exists('D:\')` 探 VB 类型、再探 COM），**不要**写完一整套再撞墙；并且**任何"删除/移动"的成败判据必须落到「目标当前状态」**，不能信 API 返回码 —— **返回码是"它自称做了什么"，目标状态才是"它真的做了什么"**。

### 37. 轮转备份三坑：名字序≠时间序 / 守卫逼你改设计 / 清场也要守规矩

**现象**（2026-10-10，V0.0.26 编辑态轮转备份）：把「保留最近 N 份」落到 `data/.bak/`，连续踩到三个坑，**每一个都是实测抓到的**。

**坑 1 · 「名字序 = 时间序」是个需要证明的前提，不是天然成立。**
首版时间戳只到**秒**，同秒内多份备份靠 `-2` / `-3` 后缀区分。但 ASCII 里 `-`(0x2D) **小于** `.`(0x2E) → `editor-X-2.json` 排在 `editor-X.json` **之前**。更要命的是：一旦某份旧备份被裁掉、**它的名字被后一次保存重新占用**，新文件就排到已有后缀文件**前面** —— 「保留最近 N 份」于是把**刚写的那份**当最旧淘汰（实测：第 6 次保存后，`.bak/` 里最新的是**第 4 版**）。
**修法**：① 时间戳加**微秒**（`%Y%m%d-%H%M%S-%f`）→ 名字**全局单调**、不再复用，问题从根上消失；② 同微秒兜底后缀改用 `_NNN`（`_`(0x5F) > `.`，与创建序一致；补零到 3 位，避开 `_2 > _10` 的字典序陷阱）。
**通用教训**：**凡「用文件名/字符串代表时间先后」，都必须显式验证「排序方向 == 时间方向」**，尤其**后缀**部分 —— 分隔符在 ASCII 表上的位置决定方向，`-` / `.` / `_` 三者的相对次序足以让裁剪**反向**。还要问**名字是否可能被复用**：只要可能，就必须保证「新名字 ≥ 所有现存名字」。

**坑 2 · 守卫拦下你的新代码时，先改设计，不是改守卫。**
首版淘汰旧备份用 `Path.unlink()`，被 `verify.py` **7q 守卫当场抓住**：「routes.py 出现真删除（unlink/remove），违反『只复制不删除』」。**处置不是给守卫开例外，而是改设计** —— 淘汰改为 `shutil.move()` 进 `data/.bak/.trash/<时间戳>/`（软删除，可找回），与 `templates/.trash/` 同体例。
**通用教训**：被**既有守卫**拦下时，先问「是守卫过严，还是设计越界」。**全项目硬不变量优先**；能给硬不变量开例外的只有一次**明确的政策变更**，那是**另一个决定**，不是实现细节。副产品：轮转至此**不含任何不可逆动作**；代价是 `.trash/` 缓慢增长（与 `templates/.trash/` 同量级，可接受）。

**坑 3 · 别把「我没动手」当成「我没造成污染」。**
新增的轮转会让**既有单测**（`EditorRoundTripTests`）往**真实** `data/.bak/` 写文件 —— 因为 `setUp` 只隔离了 `EDITOR_FILE`，**没隔离新增的 `EDITOR_BACKUP_DIR`**。
**通用教训**：**新增一个会写盘的行为时，必须回头审查既有测试的隔离面** —— 隔离「一个路径」不等于隔离「这类路径」。测试隔离要按**写入点**枚举，不是按被测函数枚举。

**验证**：反向验证（临时副本把时间戳改回秒级）→ `test_prune_never_drops_the_newest` **精确 FAIL**（`'editor-20261010-233000.json' not found in ['…_002','…_003']`），主线同用例 **OK**；四件套 **82/0 · 198 OK · 17/0 · 9/9**。

### 38. 反向验证，还要反过来验「用例本身能不能抓到」——不同名文件骗过了「撞车」用例

**现象**（2026-10-11，`tools/` §P2 整改 · 组 1 · P2-5）：给 `store.py`「checkout 回收目录同秒不撞」补测试。初版用例的做法是：同一秒内连续两次 `checkout`，各自回收一个**新文件**（`extra_a.py`、`extra_b.py`）。

**问题**：这两个文件**不同名** —— 即便两次 checkout 真的共用了同一个回收目录，它们也**互不覆盖**、都能幸存，于是断言「两份都在」**永远成立**。**这个用例根本抓不到「同秒撞目录」这个缺陷**：它看起来在测「撞车」，实际只测了「两个不同名文件能共存」。

**修法**：把两次回收改成**同一路径 `src/extra.py` 的两次不同内容**（模拟「首次回收后，用户又在原路径建了同名文件」）—— 此时若两次 checkout 撞进同一回收目录，**第二次会覆盖第一次**，断言「两份回收副本内容分别为 `"A\n"` / `"B\n"`」就会 FAIL。

**验证**：注入缺陷（去掉防撞序号）→ 该用例**精确 FAIL**；基线 PASS。

**通用教训**：**「反向验证」的对象不只是被测代码，还包括测试用例本身**。一个用例能 PASS，可能不是因为它验证了目标行为，而是因为**它构造的输入压根触发不了那个缺陷**（本例：不同名文件天然不冲突）。所以对每个「防撞 / 防覆盖 / 防重复」类断言，都要问一句：**「我喂进去的输入，真的会把出错路径逼到台面上吗？」** 若两个样本**天然互斥**（不同名、不同键、不同范围），那撞车与否根本不影响结论 —— 这类用例是「看着在测、其实没测」。与 §三.34「有测试 ≠ 测到要害」同族，但更隐蔽：**前者是没写测试，后者是写了测试、却测了个寂寞。**

### 39. 报告结论也要逐条对着盘上源码核 —— 两条「问题」经实测站不住

**现象**（2026-10-11，`tools/` §P2 整改）：把《审查报告_工具链_20261010》§四 P2 台账 19 项**逐条对照盘上源码复核**，发现**两条的事实前提不准**：

| 报告原话 | 实测 | 性质 |
|---|---|---|
| `--against V0.0.1@rX`（X 非数字）→ `rev=None` → **静默回退到最新修订** | 实为 **FAIL「无法判定」**（**未**回退） | **现象证伪**（安全方向）；仅残留「文案不精确」 |
| P2-14：体积上限项包在 `if src_files:` 内 → `src/` 缺失时该项**不产生（少一项而非 FAIL）** | 在**最小根**（只含 `tools/` + `tests/` + `VERSION` + `start.bat`）上，`verify.py` **L1027 无守卫 `read_text()`**（读 `src/web/js/i18n/zh-CN.js`，同段 L1018 / L1024 均有 `is_file()` 守卫）→ 缺 `src/` 时**直接 Traceback** | **前提不精确**（实为**先崩溃**，到不了该项） |

**处置**：**P2-3** 按「文案订正」结案（现象为安全方向，只需把报错文案写准，**不补默认值**）；**P2-14** 仍按「缺 `src/` 显式 FAIL」处置组 2 改动，**L1027 崩溃点如实记录、未顺手修**（超出本轮裁定范围）。

**通用教训**：**审查报告的每条结论都要落到盘上复现，不能照单执行。**
① **「方向」也要核**：报告写「静默回退」，实际可能是「显式失败」（更安全）；照单「补个默认值」反而把**安全降级**，**修错方向**；
② **前提也要核**：报告的因果链（「包在 `if` 内 → 少一项」）可能被**更早的一道无守卫读取**截断（先崩溃），此时真正要修的是那个崩溃点，而非报告指的地点；
③ **核实中发现的新问题若超出本轮裁定范围，如实记录、不擅自扩大改动面** —— 「顺手修」会让一次可回滚的小改动**边界模糊**，反而增加风险。这与 §三.35「说得和做的不一样」互补：**那条讲代码与文案脱节，这条讲报告与实况脱节。**

### 40. 「守卫自己崩了」比「守卫报错」更危险 —— 崩溃点会遮蔽其后的所有检查

**现象**（2026-10-11，收口第 23 项附带发现）：`tools/verify.py:1027` 读 `src/web/js/i18n/zh-CN.js` 时**无 `is_file()` 守卫**（同段 L1010 / L1018 / L1024 均有）。缺 `src/` 时，`verify` 在**该行直接 `FileNotFoundError` Traceback**。

**为何危险**：这门禁的困境在于 —— **它本应用来报告「`src/` 缺失」，却在缺 `src/` 时自己先崩了**。更糟的是**遮蔽效应**：该行**排在**「体积上限」检查**之前**，于是组 2 刚做的 **P2-14「缺 `src/` 显式 FAIL」修复根本执行不到**（被崩溃抢先）—— 门禁表现为「一整屏 Traceback」，而**真正该看到的那条 FAIL 一条都不出现**。**「没报错」≠「没问题」；「报了错」也可能因为崩在更前面，而独独漏掉该报的那条。**

**修法**：补 `is_file()` 守卫（与同段 L1010 / L1018 / L1024 同款式，缺文件取空串）。

**侦察要穷尽**：全文 **19** 个 `.read_text()` 调用点逐一判定 —— 18 处受保护（`glob`/`rglob` 循环 · `try/except (OSError…)` · 前置 `is_file()`），**仅此 1 处无守卫**。**不要因为发现一处就当「遍地都是」，也不要因为修好一处就当「全好了」** —— 逐点核。

**验证（修复前后对照，最小根）**：修复前 → L1027 `Traceback`、**无「体积上限」行**；修复后 → `Traceback` **0 次**、「体积上限」**`[FAIL] 未找到 …\src 下任何文件（src/ 缺失？）`** 如约出现。

**通用教训**：**「先崩」与「少一项」是两种完全不同的病因，用同一句「少一项而非 FAIL」概括会掩盖真因**（同 §三.39）。对**门禁 / 校验类脚本**，凡 `read_text()` / `json.loads()` / 子进程调用等「可能因缺件抛异常」的语句，**要么前置存在性判据、要么就地兜底**；且**检查顺序本身有意义** —— 一个崩溃点会吃掉**它之后**（而非之前）的所有检查。判断门禁是否健康，不能只看「有没有红」，还要看**「该红的那条，到底有没有机会被打印出来」**。

### 41. 升版顺序：bump → 同步版本戳 → store commit（次序错一步，快照装错内容）

**现象**（2026-10-11，`src/` 审查批 1 → V0.0.27）：升 patch 版时我按「bump → store commit → 同步版本戳」执行，结果 `store.py commit` 打出的 `V0.0.27@r1` **装的是旧版本戳** —— 紧接着 `verify --against V0.0.27` 立刻报 **3 项 FAIL**：

```
[FAIL] 版本兜底一致 §P0-3 L1   VERSION=V0.0.27，取词表写死为 en-US.js=V0.0.26 / zh-CN.js=V0.0.26
[FAIL] 共享契约版本戳          漂移：schema.json version=V0.0.26 ≠ VERSION V0.0.27（须同步）
[FAIL] 接续说明实况段          已过期
```

**根因**：`bump` 只改了 `VERSION` **一个**文件，而「版本号」在项目里是**四处联动**的：`VERSION` · `src/web/js/i18n/{zh-CN,en-US}.js` 的 `help.versionFallback` · `src/shared/schema.json` 的 `version`。`store.py commit` 打的是**「此刻盘上受跟踪文件」这个组合** —— 只要有一处尚未同步，快照就是**自相矛盾**的（新版本号 + 旧版本戳）。

**修法**：补一次 `store.py commit` → 生成同版本修订 **`V0.0.27@r2`**（`@r1` 保留、未发布、可弃；项目原生支持同版本多修订，故**无需删目录** —— 也就避免了不可逆动作）。

**通用教训**：
① **升版是一组「联动作业」，不是一个 `bump` 命令** —— `VERSION` 只是**主键**，凡**写死版本号**的衍生处（i18n 兜底 / 契约版本戳）都必须一并同步，且**必须在 `store commit` 之前**。
② **`store commit` 是一面镜子**：它照出「此刻盘上的组合是否自洽」。**先 commit 后补同步**不会即时报错，只会在 `--against` 时**延迟暴露** —— 而 `--against` 正是为「快照 ≠ 期望」准备的门禁。**它报的 FAIL 里，这一条往往不是「代码错」，而是「流程次序错」。**
③ **补救优先「追加修订」，不用「删除重来」**：`@r2` 与「删 `versions/V0.0.27/` 重新 commit」结果等价，但前者**零删除动作**（符合「只复制不删除」硬不变量）、可回滚。**能靠追加解决的，不要动删除。**

### 42. 审计清单里的「现象」必须先实证复现，再据以改动（C-P3-1「滚动回顶」未复现）

**现象**（2026-10-11，`src/` 审查批 3）：《审查报告_src_20261011》§三 C-P3-1 记「`ui/tree-view.js` 的 `render` 全量重建 DOM → 每次编辑都重渲染 → **滚动位置回到顶部**（体验明显）」。据此我改了 `render`（重建前后显式存 / 还原滚动位置），并按纪律做**反向验证**：把 `render` **还原成原实现**跑 `browser_smoke` —— **期望该项 FAIL，实际仍 PASS**（`scrollTop 40 → 40，重建 是`）。

**深挖**：再关掉 `overflow-anchor: none`（排除"滚动锚定"解释），**仍 PASS**。根因：`render` 是 `container.textContent = ''` **紧接** `appendChild(...)`，**同一任务内**完成；浏览器在两次 DOM 变更之间**不重排**，于是 `#treeWrap` 的 `scrollHeight` 从未真正变 0，**从不夹紧 `scrollTop`** —— 原实现**本就保持了滚动位置**，报告所述"回到顶部"**在本机不可复现**。

**后果与处置**：该条目疑为**静态阅读推断**（见"全量重建"即推"滚动丢失"），未实证。据实记为**未复现**；经用户裁决，改动保留为**显式保持**（对未来若改为**异步渲染 / 强制回流**更稳健），`browser_smoke` 断言则当**前向行为守卫**（今日必过，日后被破坏则报警）—— **而非"抓本次回归的探针"**。

**通用教训**：
① **审计 / 评审文档的「现象」列不等于事实** —— 它与「建议」不同，**必须先在盘上复现**才能据以改代码；否则是对影子动手，还会污染版本记录（"修了个不存在的问题"）。
② **反向验证的"意外 PASS"是金子**：还原后**没** FAIL，正是**证伪前提**的证据 —— 不要因为"改都改了"就把它藏起来；**据实记录比看上去漂亮更重要**。
③ 判定"重建是否真的发生"要**另设判据**（本例用"首行节点对象被替换"，`m.reRendered`），否则重建没发生时的"滚动未变"会造出**假通过**。

### 43. `browser_smoke` 探针阶段数受 `--virtual-time-budget` 约束 —— 多一个 iframe 就整体超时

**现象**（2026-10-11，同批）：给 `browser_smoke` 新增皮肤 / 箭头检查时，我另起了一个独立阶段（第 4 个 `frame('./index.html', …)`）。重跑 → **`[FAIL] 浏览器运行 120.0s 内未返回`**，连带「控制台日志通道可用」「探针完成」全 FAIL（退出码 `-1`）。

**根因**：探针以 `--virtual-time-budget=20000`（20 s 虚拟时间）跑**顺序 iframe 阶段**；每个 `frame()` 用 `setTimeout(tick, 25)` 轮询、最多 `240` 次 → **单阶段上限 6 s 虚拟时间**。原本 3 阶段 ≈ 18 s（在预算内）；**加到 4 阶段 ≈ 24 s > 20 s** → 预算耗尽前跑不完，浏览器**不退出**，结果行永不写出。

**修法**：**把新检查并入既有阶段 1**（偏好与页面都已就绪，只多读两个指标），阶段数维持 3，总虚拟时间回落预算内 —— 重跑即 **14/0**。**不必**调大 `--budget`（那会拖慢每次门禁）。

**通用教训**：给"顺序多阶段"的探针**加检查时，优先"并入既有阶段"而非"新起阶段"**；新起阶段要计入 **阶段数 × 单阶段上限** 对 `--virtual-time-budget` 的挤压。**超时的表现常常不是"某一项失败"，而是"所有项一起消失"**（结果行压根没写出）—— 遇到「退出码 -1 + 探针完成 FAIL」要先怀疑**预算 / 阶段数**，而不是去查页面代码。

### 44. Windows 下 `Path.write_text` 默认把 `\n` 翻成 `\r\n` —— 改写源码的脚本必须显式 `newline="\n"`

**现象**（2026-10-11，`src/` 审查批 4A）：反向验证驱动脚本用 `path.write_text(text)` 做「注入 → 验证 → 还原」。跑完后 `git diff --stat` 显示 `routes.py` 改动 **1504 行**（实际只改了 62 行）—— 整个文件被重写了。

**根因**：`Path.write_text(s)` 底层 `open(mode="w")` 的 `newline=None` 会做 **`\n` → `os.linesep`** 翻译；Windows 上 `os.linesep == "\r\n"`。而项目源码是 **LF 基线**（§编码基线），`read_text` 又把 `\r\n` 归一为 `\n` —— **一读一写把整份源码从 LF 翻成 CRLF**。`verify.py`「换行一致性」直接读字节，会立即报警。

**修法**：改写源码的脚本一律 `path.write_text(s, encoding="utf-8", newline="\n")`（或直接 `read_bytes`/`write_bytes`）。已在反向验证脚本中固化。

**通用教训**：任何**会写回源码**的自动化（反向验证、批量替换、格式化、代码生成器）**必须显式保 LF**；不要依赖编辑器的"自动 EOL"，也不要以为 `.gitattributes` / `core.autocrlf` 能兜住 —— **git 层可能被掩盖，但 `verify.py` 读的是磁盘字节，一定会抓到**。判据落在字节层，任何"保存"动作都要对它负责。

### 45. 前端「递归 → 显式栈」的两个真坑：栈溢出的**触发量级**要实测，栈里**别塞长字符串**

**现象**（2026-10-11，`src/` 审查批 4B，B-P3-5 查询族改造）：把 `findNode` / `findParent` / `isSelfOrDescendant` / `pathOf` / `depthOf` / `inspector.findAny` 由递归改显式栈，顺手做反向验证 —— 结果踩了两个坑。

**坑 1：栈溢出的触发层数，凭直觉估会“估高一个量级”**。初版深树用例取 **5000 层**，把 `findNode` 退回递归、跑单测 —— **通过了**（`V8` 没溢栈）→ 反向验证「未复现」= **假红**。改 **20000 层**（＝ `MAX_EDITOR_NODES`）后递归版**必** `RangeError`。
> **通用教训**：`MaxCallStackSize` 是**运行时、版本、函数帧大小**的函数 —— 帧越小、能递归的层数越多。**不能用“猜一个够大的数”**；判据应当锚到**项目自身的真实上限常量**（本例即 `MAX_EDITOR_NODES`），这样用例同时具备「量级真实」与「语义自解释」两个性质：**深到业务允许的最深处**。

**坑 2：显式栈初版把「整条路径字符串」压进栈 → 线性深链下退化成 O(深度²)**。`pathOf` 第一版让栈里携带「父路径 + 名」的累积串，深链 20000 层时中间串累计吃掉上 GB，反而**比递归更糟**。
> **修法**：改**父指针映射** —— 先一趟遍历建 `Map<child, parentNode>`（O(n)），再自目标结点顺父指针回溯拼名（O(深度)），**总复杂度 O(n)**。
> **通用教训**：把递归改迭代时，**别把「递归的参数累积」原样搬进栈帧**。「累积型参数」（路径、深度、前缀、累加值）在递归里是 O(1) 的栈帧局部量，搬到显式栈上就变成**每帧一份的拷贝**。要么**改成父指针/后序回填**，要么**显式拆成两趟**（一趟定位、一趟回溯）。改造后**必须复盘复杂度**，不能只验「不溢栈」。

**副坑：告警串也要过取词表守卫**。`toPlainTree` 的重名告警初写中文，立刻被 `verify`「JS 文案经取词表 §P0-3 L1」判红（`src/web/js/**` 不得直写中文，`console.warn` 也算）→ 改纯 ASCII `'[QingMan] toPlainTree: duplicate sibling name overwritten:'`。**开发者可见的调试文案走 ASCII，用户可见文案走取词表**，两者别混。

### 46. 新写的守卫先抓到了自己的错 —— 锚点要锚在「该文件里真实存在且只会出现在代码里」的串上

**现象**（2026-10-11，`src/` 审查批 4C）：本批新增`verify.py` 检查段「UI 防御批 V0.0.32」+ 「浏览器冒烟覆盖」3 个锚点，加完**第一次跑 verify 就红了**，两条，且**都是守卫写错了**，不是被测代码有问题：

1. **锚点归属搞错**：「浏览器冒烟覆盖」那一段查的是 `tools/browser_smoke.py` 的文本，我却把 `isSelfOrDescendant(draggingNode` / `leftRow` 这两个 **`tree-view.js` 里的 token** 写了进去 —— 它们**永远不可能**出现在 `browser_smoke.py` 里，判据恒红。
2. **注释里的字面量被判据当真**：「UI 防御批」有一条「旧判据已清除」的检查（`"draggingId !== node.id" in tv`，防两套判据并存）。而我在 `dragover` 上方的新注释里**引用**了旧写法（为了讲清「旧实现只挡自身」）—— 判据读到注释里的这个串，误报「旧判据仍残留」。

**处置**：
* 锚点改锚**探针自己的指标键**（`dragDesc` / `dlChild` / `MAX_TOASTS`）—— 这些是「探针产出、判定消费」的契约名，改动必然成对，天然适合当锚点。
* 注释改写措辞（「仅比 id 是否相等」），**判据保持最大强度**——不为迁就注释而放松匹配（放松了它就不再能抓真正的回退）。

**通用教训**：
* **写锚点前先在目标文件里 `grep` 一次**：「这个串真的在这个文件里吗？」—— 跨文件搬运 token 是最容易犯的锚点错误，而它的表现是**恒红假失败**，会浪费更多时间去查被测代码。
* **锚点要锚在「只可能出现在代码里」的串上**。注释是判据的天然干扰源：`in text` 这种朴素子串判据**分不清代码与注释**。两种解法 ——（a）换一个不会出现在注释里的串（如带 `if (` 前缀的整句）；（b）像本例一样改写注释。**不要**改判据去跳过注释行（注释风格多样，跳过规则一复杂就产生新盲区）。
* 「守卫先抓到自己的错」其实是**好消息**：说明守卫真的在跑、真的能红 —— 一次性写完就全绿的守卫，反而要先怀疑它是不是根本没生效。

### 47. 自查的「用例」与「驱动」也会错 —— 断言不合预期时先分清是实现错还是用例错

**现象**（2026-10-11，`src/` 审查批 4D · 序列化族迭代化）：本批是**自查项**（报告未列、自行发现），结果**两处错误都出在我自己的验证工具上**，不是被测代码：

1. **用例断言写错**：深链（20000 层）用例里，我把叶子文件挂在**最深处**的目录下 → `children[0]` 下潜比预想**多走一跳**，`depth` 实测 **20001**（断言写的是 20000）→ 单测红。**实现是对的，是用例的树形写错了。**
2. **驱动取错流**：反向验证驱动用 `subprocess` 抓 `stdout` 解析单测结果 —— 但 `unittest` 的结论（`Ran N tests` / `OK` / `FAIL:`）**全部写 stderr**，于是 `stdout` 为空、解析集合恒为空集，表现为「注入缺陷后单测**没有新增失败**」→ 差点误判成「缺陷未复现」（其实是驱动根本没读到）。

**处置**：
* 用例：改成「最深处留**空目录**（下潜恰为 20000）+ 文件挂**根下**」；断言值按实测修正。
* 驱动：解析 `stdout + "\n" + stderr`；并把「**基线副本必须全绿**」也设为一个显式判据（基线不绿即先判驱动本身有问题）。

**通用教训**：
* 断言失败时，**先分清「实现错」还是「用例 / 断言错」** —— 本批两次都不是实现问题。若先入为主去改实现，会把对的代码改坏。
* **脚本化取数要两个流都读**。各工具的「结果流」约定不同：`unittest` 走 **stderr**，多数 CLI 走 stdout。宁可 `stdout + stderr` 合并解析，也别赌一个。
* **给验证驱动自己加自检**（如「基线必须 0 失败」）：驱动写错时的表现，往往与「缺陷不存在」一模一样 —— 自检是唯一能把二者区分开的信号。

### 48. 「独立探针」也不能凭记忆写 —— 全新探针首跑 FAIL，先按「探针 / 代码 / 环境」三分

**现象**（2026-10-11，P2 跨批合并回归）：为做一次「另起角度」的合并回归，我凭**记忆**写了一个 Node 探针，直接调用 `tree-model` 的 `canMove` / `moveNode` / `renameNode` / `findParent` / `depthOf` / `countTree`。**首跑 18 条里 7 条 FAIL**，看上去像「四批合并引入了 7 个缺陷」。读源码（`@returns` 注释 + 实现）后确认：**7 条全是探针写错了 API 契约**，被测代码没有任何问题：

1. **`canMove` / `moveNode` 返回的是原因码字符串** `true | 'missing' | 'notDir' | 'cycle' | 'exists' | 'root'`，不是布尔 —— 我却断言 `=== false`；而 `'root'` 恰恰是「根节点不可移动」的**正确**返回。
2. **`countTree` 返回 `{dirs, files}` 对象**，我当数字比（`===` 恒假）。
3. **`depthOf` 以 root 为 0 起算**（深层返回 300），我按「root=1」断言 301。
4. **`findParent(root, id)` 返回的是「父节点」**，我却拿**被查节点自身**去比。
5. **重名用例的判据上下文对不上**：把重复文件加在 `root` 下，却拿**父为 `d298`** 的节点去改名 —— 二者不同层，当然不冲突。

**处置**：按真实契约逐条改写断言 → **18/18 通过**。

**通用教训**：
* **写探针前先读被测函数的返回契约**（`@returns` / 实现体），别用「大概是布尔 / 数字」的直觉。JS 无类型标注时尤其容易踩 —— Python 有注解兜底，JS 只能靠读。
* **全新探针首次 FAIL，先按「探针错 / 代码错 / 环境错」三分**，再动手改代码。这与 §三.47 同源：**断言不合预期时，第一反应应是怀疑断言，而不是怀疑实现**。
* **反向验证**（注入已知缺陷）的价值在于「已知正确 vs 已知错误」的对照；而**正向探针**必须先自证「探针与代码说的是同一门语言」—— 否则成片的假 FAIL 会**淹没真实信号**（本例 7 假 0 真，若不加甄别就会误改为「修 7 个 bug」而把对的代码改坏）。

### 49. 源码注释里的 `§` 引用只认「项目约定.md 的编号」+ 计数别照抄旧文档

**现象**（2026-10-11，P3 · 6A 模板双格式）：

1. **`§` 引用被判悬空**：我在 `src/server/dtree_core.py` 的注释里写了 `§十.3`（本意指向《项目手册》第十节）。`verify` 的「源码 § 引用可解析」立刻红：`指向不存在的编号：『十』`。原因：该守卫**只从 `docs/项目约定.md` 的标题行收集合法编号**（`P0-1` / `P2` / `编码基线`…），而 `§十.3` 的标签经正则 `§([A-Za-z0-9]+(?:[.-][A-Za-z0-9]+)*|[\u4e00-\u9fff]+)` 截出的是 `十`，不在该集合里。**改指 `§P2 第 7 项` 后通过。**
2. **计数照抄旧文档出错**：设计文档与手册长期写「工具内置 **17 套业务模板** + P0 空模板 = 18」。实测 `ls templates/*.json | wc -l` = **17**，拆开是 P0–P9（10）+ S2–S8（7）→ **业务模板只有 16 套**。旧数字**整体多算一套**。

**处置**：
* 源码里凡是 `§xxx` 引用，**先用 `grep` 确认该编号在 `docs/项目约定.md` 的标题里真实存在**；要指向项目手册 / 其他文档，就写**书名号或文件名**（如 `《模板系统重设计_方案原型_20261011》`），不要写 `§` 编号骗过眼睛、却被守卫判悬空。
* 计数一律**从盘上现场数**（`ls | wc -l`、`find | wc -l`），不抄旧文档里的数字；本处已在设计文档与手册**据实更正为「P0 + 16 套」**。

**通用教训**：
* **守卫的「已知集合」来自何处，决定了你的引用该怎么写**。这条守卫的集合是 `项目约定.md` 的标题 —— 它**不是**「所有文档的 § 都能解析」。写引用前先问「这个编号在**那一个**文件里定义过吗」。
* **「陈旧计数」是最隐蔽的一致性缺陷**：它不会让任何测试变红，只会让人基于错数字做判断。凡涉及「套数 / 项数 / 条数」，**现场数一遍**再落笔（与 §三.47「断言先用例错」同源：先核实，再断言）。

### 50. 「同一条拒绝规则」在不同场景的严格度可能必须不同 —— 判据要为「场景」命名，不是为「概念」命名

**现象**（2026-10-11，P3 · 6B 模板目录绑定）：初版只想写**一个**判据函数 `_templates_dir_blocked(path)`，回答「这个目录能不能用」，然后**同时**拿它去做两件事：

1. **绑定校验** —— 用户通过 `PUT /api/templates-dir` 选定目录时，拦掉不该指向的地方；
2. **运行态校验** —— 每次 `list_templates` / `save_template` 时，检查当前生效目录是否合法。

写完跑测试立刻红了：**默认模板目录 `templates/` 被判非法** —— 因为它位于 `PROJECT_DIR` 之下，而「拒自绑」恰恰要求**拒绝项目自身及其子树**。这直接导致**工具一启动就「模板库不可用」**、`save_template` **恒抛错**：**默认路径被自己的守卫拦死**。

**根因**：这两件事的**严格度本就不同**，却被一个「概念名」（能不能用）盖住了差异。

| 场景 | 默认 `templates/` 应否通过 | 严格度 |
|---|---|---|
| **绑定**（用户显式指定落地目录） | **否** —— 不许绑到项目自身，否则用户把模板写进交付目录 | 严 |
| **运行态**（当前生效目录是否可用） | **是** —— 出厂默认就是它，它**先天合法** | 宽 |

**处置**：拆成两个函数，各按自己的场景命名 ——

* **绑定判据** `_templates_dir_blocked(path)`：**严**。拒内置 `templates/` 本身 / `PROJECT_DIR` 及其祖先 / 黑名单子树 / 黑名单根本身。
* **运行态判据** `_templates_dir_reason(path)`：**宽**。**默认模板目录先天合法**（直接放行），其余才回落到绑定判据。

并补两条回归用例把语义钉死：`test_default_dir_is_valid_not_blocked`（默认目录**不被**绑定判据拒）、`test_default_dir_lists_normally`（默认目录**正常列表**，不是 `available=False`）。

**通用教训**：
* **一个「概念」落到不同调用点，常常需要不同的严格度**。把判据命名成「能不能用」这类**笼统概念名**，就会诱使你在多个场景里复用它 —— 而每个场景的边界条件并不一样。**按场景命名**（`_blocked` 给绑定 / `_reason` 给运行态），差异就写在名字里，不会被顺手合并。
* **默认值必须被自己的守卫放行**：任何「拒绝规则」上线前，先问一句「**出厂默认值能过吗？**」。本例里默认路径在 `PROJECT_DIR` 之下，天然会撞上「拒自绑」—— 若只有一个函数，**默认路径必被拦死**，且症状是「工具一开机就报模板库不可用」，很容易被误当成「模板目录本身有问题」而去修配置，**越修越远**。
* 这与 §三.42（审计现象先实证）同向：**别急着改配置 / 改实现，先问「判据在默认输入下结论对不对」**。判据本身是错的，改多少配置都白搭。

### 51. 前缀匹配的「集合路由」会吞掉「具体路由」—— 且守卫别只锚变量名

**现象**（2026-10-11，P3 · 6C 模板双格式 + 导入）：新增 `POST /api/templates/import` 后，`do_POST` 里原本这段判定把它**吃掉**了：

```python
is_rename = path.startswith(routes.TEMPLATES_PATH + "/")   # /api/templates/
if not is_rename and path not in (...):
    self._fail(404, "notFound", path=path); return
```

`routes.TEMPLATES_PATH` 是 `/api/templates`，于是 `/api/templates/import` **也满足** `startswith("/api/templates/")` → 被当成**「重命名一个叫 `import` 的模板」** → `rename_template("import")` → `_template_path_or_raise` 白名单不过（`import` 没有扩展名）→ 报 `templateNotFound`。功能看着「没生效」，但错误码指向模板不存在，**很容易误判为前端没发对请求**。

**根因**：两条路由**共享前缀** —— `/api/templates/<name>`（**集合**：任意名字）与 `/api/templates/import`（**具体**）。`startswith` 是**前缀**判定，不区分「段」；只要集合路由先判，具体路由永远被吞。

**处置**：
* **具体路由先匹配**，且让集合路由显式排除它：
  ```python
  is_import = path == routes.TEMPLATES_IMPORT_PATH
  is_rename = (not is_import) and path.startswith(routes.TEMPLATES_PATH + "/")
  ```
* **守卫锚点从裸变量名收紧为完整判定表达式**：最初 verify 里锚的是 `"is_import"` 这个 token —— 把实现退化成 `is_import = False` **照样能过锚点**（字符串还在），而单测**根本不经过 `app.py` 的路由层**（测试直接调 `routes.import_template`），于是这个回归**三层都抓不到**。改锚 `is_import = path == routes.TEMPLATES_IMPORT_PATH` 后，退化写法立刻被守卫抓住（反向验证 **N8** 命中）。

**通用教训**：
* **「集合路由 + 具体路由」共享前缀时，具体路由必须先匹配**。这是 REST 路由的经典陷阱（`/users/me` vs `/users/<id>`）。本项目的路由是手写 `startswith` / `==` 分支，**没有框架帮你排序** —— 新增具体端点时，第一件事就是把它的判定**提到集合判定之前**。
* **守卫别只锚「变量名」，要锚「判定表达式」**。锚点太松 = 守卫形同虚设：`is_import` 在、但值是 `False`，语义已死而守卫仍绿。这与 §三.46（锚点要锚在「只可能出现在代码里」的串上）同源 —— 本例更进一步：**同一行里，锚「名字」还是锚「赋值」决定了守卫有没有牙**。
* **路由层是单测盲区**：`tests/` 直调 `routes.*`，绕过 `app.py` 的路径分派。凡是「接线 / 分派 / 顺序」类缺陷，**单测天然抓不到** —— 只能靠 `verify` 守卫（静态锚点）或 `smoke`（真起服务走 HTTP）兜。给分派逻辑上锚点，不是形式主义。

### 52. 「删除到回收站」的四个坑：时间戳是 UTC、返回码不可信、目录口径会双算、脚本会删掉自己的输出

**背景**（2026-10-11，6A/6B/6C 批次临时件清理）：把 `E:\qm_revcheck_6C\`（75 文件）与 `%TEMP%` 下 24 条 `qm_*`（412 文件 / 191 目录 / 9028050 B）送回收站。删除本身一次成功，**难点全在「怎么证明它真的落进了回收站且可还原」**。

**坑 1：`$I` 的「删除时间」字段是 UTC，不是本地时间。**
`$I` 结构为 `[0:8] 头 + [8:16] 文件大小 + [16:24] FILETIME(删除时间) + [24:28] 路径长度(字符,含 \0) + [28:] UTF-16LE 原路径`。首轮按**本地时间**划窗口（「最近 60 分钟 = 本批次」），结论是「本批次记录 0 条、命中的全是 08:08–15:44 的历史记录」——**恰好反了**。受控实验定性：新建探针 → 回收 → 立刻读回，`[16:24] → 2026-10-11 15:55:43.573`，而当时**本地 23:55:43 / UTC 15:55:43**。改按 UTC 划窗后，「本批次」与「历史」立刻分离。
⚠️ 更隐蔽的是：**同一路径的历史记录会与本批次记录并存**（`qm_editorbak_enfmr6p0` 删除前实测 0 文件，站内却有 5 文件——那是本地 16:08 那轮删的），所以「站内计数 ≠ 删除前计数」不能直接判为丢失，**必须先按时间归因**。

**坑 2：`SHFileOperationW` 的返回值不能当成功判据。**
5 种子情形微测（**新建文件 / 完全不存在路径 / 有内容目录 / 空目录 / 同路径连删两次**）**全部返回 `RC=2`**，而每次源路径都消失；批量里两个大目录返回 `RC=0`、其余 22 条返回 `RC=2`，**两者均已成功删除**。故权威判据只能是 **「源路径消失 + `$I`/`$R` 记录存在（且删除时间落在本批次窗口）」**；`RC` 连同 `fAnyOperationsAborted` 一并**不采信**。

**坑 3：目录目标的「站内」计数口径 = 顶层 `$R` 子树内容 + 各子项独立 `$I` 记录。**
Windows 对部分子项**单独建记录**、其余留在顶层 `$R` 骨架里。只数 `.json`/文件记录会**漏**（`qm_browser_r5u_7k7h` 漏 6 文件 / 91198 B）；只走顶层 `$R` 子树也会**漏**（`qm_browser_probe_n9nj5aat` 走 `$R` 仅得 0 文件）。合并两种口径后：24/24 全项一致，合计 **412 文件 / 191 目录 / 9028050 B** 与删除前**逐字节吻合**。

**坑 4：清扫脚本会把自己（和自己的输出）删掉。**
`python sweep.py > "%TEMP%/qm_sweep_out.txt"` —— 重定向文件在脚本运行前就创建，**匹配上了脚本自己的 `qm_*` 通配**，于是在核验前被删走，输出全丢（`cat: No such file or directory`）。解法二选一：① 输出文件不落在被清扫目录 / 不用同前缀；② **让脚本把自身也列入目标** —— 实测 Windows 允许删除**正在执行**的 `.py`（CPython 读毕即关文件句柄），自含清扫一次到位。

**通用教训**：受限环境下的「可还原删除」，**判据要可复算、归因要按时间**。工具返回码、路径前缀、单一目录口径，三者任缺其一，都会得出**方向错误的结论**——而这类结论恰恰最像「有据可依」。

### 53. 6D 两坑：「只按一种扩展名收集」会让孤儿静默消失；「二进制产物」会撞上全树换行扫描

**坑 1：孤儿 `.md` 静默消失（集合「少一套」而不报错）。**
`pack_templates.discover()` 原先只 `glob("*.json")` 收集，再要求每套有同名 `.md`。单测把某套 `.json` 删掉后断言「应报错」，结果 **`PackError not raised`** —— 因为 `.json` 一没有，这一套就**根本不进入集合**：套数由 17 悄悄变 16，校验、清单、zip **全部照常通过**。这正是「少一套」的典型静默失效（与 §三.32「集合少项」同源）。
**处置**：盘点上**双向**判据 —— `.json` 无同名 `.md` → 报「缺同名 .md」；`.md` 无同名 `.json` → 报「孤儿 `.md`」。后者需要一个**显式白名单** `PACK_DOC_FILES = ("模板库来源说明.md",)`，否则说明件（本就无 `.json` 等价件）会被误判为孤儿。
**连带修**：`PackError` 在 `main()` 里**未捕获** → 用户拿到的是 traceback 而非可读结论。改为**退出码分层**：`1` = 环境/IO（目录或内置件缺失）；`2` = 内容校验不通过（等价性/规范渲染/孤儿/清单不一致）。

**坑 2：二进制产物进入「全树换行扫描」→ 假红。**
新增 `templates-pack/QingMan-模板包.zip` 后，`verify` 的**换行一致性**项立刻 FAIL：`templates-pack/QingMan-模板包.zip(含 CR)`。该检查按「纳入版本控制的**文本**文件全集」遍历全树，二进制只按**扩展名白名单**豁免（`BINARY_SUFFIXES`）—— deflate 流天然含 `0x0D` 字节，于是被当成「CRLF 违规」。
**处置**：把 `.zip` 登记进 `BINARY_SUFFIXES`（顺带覆盖 §P1-4 约定的 `legacy/trash-archive-<日期>.zip`）。注意 `templates-pack/*.zip` 已被 `.gitignore` 忽略，但该检查是**遍历文件系统**而非 `git ls-files` —— 故「不入库」并不等于「不被扫描」。

**通用教训**：
* **「有什么就收什么」的收集函数，必须补一条「不该有什么」的反向判据**；否则漏项表现为**数字变小**，而数字变小从不报错。
* **新增二进制格式时，记得同步所有「按扩展名判文本」的守卫**（本项目目前只有 `BINARY_SUFFIXES` 一处，但它是**全树**生效的）。

### 54. 退出码「分层」写进了 docstring，却没落在实现上 —— 反向验证才照出来

**背景**（2026-10-12，6D 反向验证 N7a）：`tools/pack_templates.py` 的 docstring 明文写着

```
退出码：0 通过；1 环境 / IO 错误（目录或内置件缺失）；2 内容校验不通过
        （等价性 / 规范渲染 / 孤儿 `.md` / 清单不一致）。
```

按此契约，删掉某一套的 `.json`（留下孤儿 `.md`）应返回 **2**。实测返回 **1**。

**根因**：这两类「内容问题」都在 **`discover()`** 里抛 `PackError`，而 `main()` 的调用点是

```python
    try:
        entries = discover(pack_dir, templates_dir)
    except PackError as exc:
        print(f"[失败] {exc}")
        return 1          # ← 环境类与内容类在这里被同一个 except 吞成同一个码
```

`discover()` 同时承担两件事：**环境探测**（包目录在不在、内置件在不在）与**内容判定**（缺同名件、孤儿 `.md`）。一个异常类型扛两种语义，`main()` 只能给一个码 —— 而它给的是**环境类的那个**。

**为什么单测没抓住**：`test_rejects_missing_json_twin` 是**直接调 `discover()`** 并断言 `PackError` 被抛出 —— 它验的是「有没有报错」，**没有经过 `main()` 的退出码映射**。行为断言覆盖了「抛不抛」，漏掉了「抛出来之后算什么」。同理 `test_missing_env_returns_1` 只验了环境类。**两条都绿，契约仍错。**

**处置**：按语义拆类，由类型承载「码位」，`main()` 分两支（子类先捕）：

```python
class PackIOError(PackError):        # 环境 / IO（包目录、内置件缺失）→ 1
    ...

    try:
        entries = discover(pack_dir, templates_dir)
    except PackIOError as exc:       # 环境类 → 1
        return 1
    except PackError as exc:         # 孤儿 `.md` / 缺同名件等内容类 → 2
        return 2
```

并补两条单测（`test_orphan_and_missing_twin_are_content_errors` / `test_missing_pack_dir_returns_1`）**从两侧**锁住码位对，verify 侧锚 `class PackIOError(` 与 `except PackIOError`。反向验证新增 **N10**（包目录缺失 → 1）与 **N7a**（孤儿 → 2）构成对偶。

**通用教训**：
* **一个异常类型不要同时承载两类语义**。当「该返 1 还是 2」需要靠调用点去分辨时，说明类型分得不够细 —— **把码位交给类型，而不是交给 catch 的位置**。
* **docstring 里的契约要有人守**。写「1 = 环境 / 2 = 内容」很自然，但如果没有测试或守卫**逐码断言**，它会在第一次重构里静默失效，而且失效方向恰恰是「看起来更保守的那一个」（统一归 1）。
* **反向验证的价值就在这类盲区**：正向单测验「注入的破坏有没有被拒」，反向验证验「拒绝的方式是否符合契约」。前者全绿，后者仍可能照出**语义层**的不一致 —— **「抓到了」与「抓对了」是两件事**。

### 55. 回收站「目录计数」的第三条口径：目标**根自身**必须排除，且大目录会被**大面积拆分**

**背景**（2026-10-12，6D 收口清理）：把 `E:\qm_revcheck_6D\`（136 文件 / 20 目录 / 1073950 B）+ `%TEMP%` 下 9 个 `qm_6d_*`（38510 B）送回收站。删除一次成功，**核验却连出两次「差异」假红** —— 都是**核验口径**的问题，不是数据丢失。

**假红 1：按「目标路径逐一精确匹配」只统计 `$R` 子树 → 文件数、字节数对得上，目录数少 2。**
首轮只把「记录路径 == 目标路径」的 10 条记录纳入，取各自 `$R` 子树求和，得 `18` 目录（实际 `20`）。原因：`os.walk` 的 `len(dirnames)` **不含子树根自身** —— `E:\qm_revcheck_6D\bak` 与 `\logs` 这两个**被单独建了 `$I`/`$R` 的目录**，其 `$R` 子树里没有它们自己，于是各少 1。

**假红 2：用「最近 N 小时」当批次窗口 → 把历史批次全捞进来。**
`%TEMP%` 下的 `qm_*` 在过去三天里删过很多轮（4A/4B/4C/6A/6B/6C 各批探针同前缀），`now - 24h` 的窗口一次命中 **32934** 条，总额虚高到 405 MB。**路径前缀 + 精确名表**才是本批的正确识别方式，时间窗只应用来**佐证「同批同簇」**（本批 133 条 E: 域记录全部落在 UTC `23:33:53–57` 这 5 秒内）。

**第三条口径（补齐 §三.52 坑 3）**：
```
目录数 = Σ(每条目录型 $I 记录的 $R 骨架子目录数)  +  记录自身数  －  1
                                                        ↑ 目标根自身要减掉
```
实测对表（本批）：骨架子目录 **18**（全在 `work\` 下）+ 记录自身 **3**（`E:\qm_revcheck_6D` 自己、`bak`、`logs`）− 1（根自身）= **20** ✅

**文件/字节口径**（同批实测）：
```
文件数 = ($R 为文件的记录数) 130  +  顶层 $R 骨架内文件 6  +  %TEMP% 目标 9  = 145  ✅
字节数 = 顶层 $I 记录 1073950  +  9 个临时件 38510  =  1112460  ✅
```
⚠️ **注意 Windows 的拆分比 §三.52 描述的更激进**：本例 136 个文件里竟有 **130 个**被单独建 `$I`/`$R`，只有 **6 个**留在顶层 `$R` 骨架内；目录侧则相反，`work\` 下 18 个目录**全部留在骨架内**，只有 `bak` / `logs` 两个被拆出。**「骨架内」与「独立记录」的比例不可预设**，必须两种都统计后相加。

**通用教训**：
* **核验脚本的「求和口径」必须先自证一遍**：同一批数据用两种口径算，若结果不同而源路径又确实消失，**先怀疑口径，再怀疑丢失**。本例两次「差异」共消耗三轮复核，全部源于口径。
* **目录计数天然会漏「子树根」** —— 凡是用 `os.walk` / `rglob` 数目录的地方，**根自身都要手动 +1**；这在回收站核验里恰好变成「+1 后再 −1（根自身不计）」，极易写错。
* **不要用时间窗代替身份判定**。前缀 / 精确名才是「这批是谁」；时间窗只回答「这批是不是同一时刻落的」，两者不可互替。

### 56. 改了「守卫函数」的判据，却忘了同步它的**单元测试** —— 22 条 FAIL 全出自这一处

**背景**（2026-10-12，6E 收口）：本批给 `tools/browser_smoke.py` 的 `verify_metrics()` 加了 **3 条** 6E 页面断言（模板目录绑定 UI / 右键菜单 5 项 / 轮询前后行数）。四件套跑到 `unittest` 时 **`FAILED (failures=22)`**，全部集中在 `tests/test_browser_smoke.VerifyMetricsTests`。

**根因**：`VerifyMetricsTests` 是**把 `verify_metrics()` 的判定逻辑固化为常态回归网** —— 它自带一份「正常基线」`NORMAL` 字典，逐字段喂给 `verify_metrics()` 并断言「全部 PASS」。本批新增的 3 条断言依赖 **7 个新字段**（`tplDirRow` / `tplDirPath` / `tplDirBtns` / `tplMenuN` / `tplMenu` / `pollBefore` / `pollAfter`），而基线 `NORMAL` **没补** → 新断言**恒缺字段 → 恒 FAIL**；同时项数断言还钉在旧值 `14`（实为 `17`），**又添一处 FAIL**。

**为什么容易漏**：`verify_metrics()` 住在 `tools/browser_smoke.py`（工具），`VerifyMetricsTests` 住在 `tests/`（测试）—— **跨文件**。改工具的人（我）脑子里只想着「给它加断言」，不会自然想到「另一份文件里存着它的基线」。而这份基线正是**为了防「断言被悄悄削弱」才存在的**，天然与工具解耦。

**处置**：`NORMAL` 补 6E 七字段 + 项数断言 `14 → 17` + 文档串同步 → `unittest` **361 OK**（`351 → 361`）。

**通用教训**：
* **凡「把某函数的判据固化成回归网」的测试，改该函数时必须同步那张基线**。这类基线有个共同特征：它是一份**期望输出的样本**（`NORMAL` / golden / fixture），而**不是**直接调用被测函数的断言 —— 后者会随实现自动跟随，前者不会。
* **反向验证要覆盖「判据数变化」**，不只覆盖「判据内容变化」。本批 9 条反向验证全是「让某条断言 FAIL」；**没有一条**在测「断言条数对不对」—— 而这恰好就是 22 条 FAIL 的成因。**项数断言**（`assertEqual(len(...), N)`）本质是「防止有人把断言删掉」的守卫，它**自己**也需要被记牢。
* 跨文件的知识点要**双向留痕**：`verify_metrics` 的 docstring 里写一句「改判据须同步 `tests/test_browser_smoke.py` 基线」，就能把这次的三轮排查压成一次提示。
