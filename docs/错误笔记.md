## 一、流程纪律（最高优先级，违反即返工）

### 1. 幻觉交付

**问题**：口头声称"已完成/已修复"，实际未真实写入磁盘。
**整改**：任何交付前必须 `ls -l` 确认真实存在；必须跑语法/完整性校验；没有校验过的文件一律不说"已完成"。

### 2. 未先确认就改 UI

**问题**：用户要求"修改前问我"，却擅自改动样式。
**整改**：UI/风格/布局类改动必须先给出具体方案（改哪个元素 → 改成什么样 → 影响范围），用户明确回复「执行」后才动手。

### 3. 越权改动

**问题**：要求"只改布局"，却顺手新增功能或改逻辑。
**整改**：改布局只动 CSS/DOM 顺序；改 BUG 只修对应问题；不"顺便"重构。

### 4. 测试污染主线

**整改**：一切试错只在 `preview/V<版本>/` 内进行（按需新建，平时该目录为空）。落地主线前必须校验通过；落地后立即 `python tools/store.py commit` 留回退点。

## 二、版本与备份纪律

1. 改主线之前必须先 `python tools/store.py commit --note "说明"`，否则该版本无回退点。
2. `versions/` 下的版本清单与 `store/objects/` 下的 blob **只增不改**，已存在的禁止覆盖。
3. 版本号采用 **SemVer 三段式**（`V<MAJOR>.<MINOR>.<PATCH>`，从 V0.0.1 起）：`patch` 修复 ／ `minor` 逻辑迭代 ／ `major` 不兼容变更。版本号只在 `VERSION` 文件维护，不在代码里硬编码。
4. **升版判据**：凡改动 `src/` 或交付契约 → 升版；纯文档、纯工具改动 → **不升版**，只在 `docs/任务进度.md` 记一条时间线。
5. 全程只复制、不删除。`checkout` 回退时「当前有、目标版本没有」的文件，先复制进 `store/.trash/<时间戳>/` 并逐字节校验，通过后才移除原文件。

## 三、技术坑点（本项目已实测）

### 1. 嵌套错误码占位符未二次填充

**现象**：报错文案出现字面量，如 `「bad/name」不是合法目录名（目录名含非法字符：{name}）`。
**根因**：`segmentInvalid` 模板里嵌了 `{reason}`，而 `reason` 自身又是含 `{name}` 的模板；只做了一层 `format`。
**修正**：内层模板格式化时必须把 `name` 一并传入 —— `message(reason, name=name)`。
**位置**：`src/server/dtree_core.py` 的 `build_tree`、`src/server/routes.py` 的 `generate`。
**状态**：V0.01 已修复，冒烟测试复测通过。

### 2. `__pycache__` 污染

**现象**：跑过校验或启动过后端后，`src/server/` 下会生成 `__pycache__`。

**根因（2026-10-09 已修）**：`tools/verify.py` 第 6 项用 `python -m py_compile` 做语法检查，**校验动作本身会写盘**。后果是「校验 → 目录被污染 → 未动文件 MD5 与快照不一致」，即检查清单里"未动文件与基线一致"这一项永远无法通过 —— 校验工具污染了自己的检查对象。

**修正**：改用 `ast.parse()` 只读解析，校验不再产生任何文件。
**位置**：`tools/verify.py` 第 6 项检查（含 `import ast` 与模块 docstring）。
**复验**：连跑两次校验，缓存残留 **0**；`src` 与 `versions/V0.01/src` 聚合 MD5 恢复一致（`95b157a1e40df6e39c4e7b5b202b7fc9`）；29 项仍全部通过。

**仍适用**：启动过后端进程仍会由 CPython 导入行为生成 `__pycache__`，运行后需清理。
**清理命令**：`find . -type d -name "__pycache__" -exec rm -rf {} +`
**兜底**：`release.py` 与 `promote.py` 均已忽略 `__pycache__` 与 `*.pyc`。

### 3. 后台服务测试后必须显式收尾

**规范**：服务必须以后台方式启动；测完必须按端口定位并停止进程，同时清理测试产物目录。
**定位命令**：`netstat -ano | grep LISTENING | grep ":8791"` → `taskkill //PID <PID> //F`。

### 4. Windows 路径引号

**规范**：`start.bat` 中一律使用 `"%~dp0"` 结尾带反斜杠的形式并用双引号包裹全部路径变量；避免裸路径拼接导致空格截断。

### 5. 静态文件的路径穿越

**规范**：拼接用户可控路径后必须 `resolve()` 并校验仍在 `web/` 内，否则返回 403。禁止直接 `web_root / url_path` 就开读。

### 6. 文件转义规则差异

- HTML 属性里 `\` 是普通字符，不需要转义。
- JS 字符串里 `\` 必须写 `\\`。
- 不要把 JS 转义规则套到 HTML 属性上，会出现双反斜杠。

### 7. 「承诺了却没实现」的检查项

**现象**：`verify.py` 里定义了 `md5()` 函数却**从未被调用**；而本笔记的交付清单写着「未动文件与快照/基线 MD5 一致」，29 项校验里**根本没有这一项**。
**根因**：规则先写进文档，实现没跟上，且缺少「检查项清单 ↔ 代码」的对齐机制。
**修正**：`verify.py` 新增 `--against <版本>` 指纹比对（SHA-256），删除该死代码；校验项 29 → **31 项**。
**教训**：**文档里承诺的每一条检查项，都必须在工具里找到对应实现**；反之，工具做的每一项检查，也应能在文档里找到出处。

### 8. 聚合校验丢失路径

**现象**：`find src -type f | xargs md5sum | awk '{print $1}' | md5sum` 这类写法只对**哈希序列**取摘要，路径不参与运算。
**后果**：文件**改名但内容不变**时，检测不出差异（曾据此误报「三份代码完全一致」）。
**修正**：清单摘要改为对「相对路径 + 指纹」按路径排序后整体求 SHA-256 —— 见 `store.py` 的 `manifest_digest`。

### 9. MD5 的适用边界

**结论**：MD5 密码学上已不推荐（碰撞可行），且多算法混用会造成口径不一。
**规范**：项目内统一使用 **SHA-256** 作为内容指纹（`store.py` / `verify.py` / `MANIFEST.json`）。历史遗留的 `SNAPSHOT.json`（MD5）保留原样，不再扩展。

### 10. 测试失败要先分清「产品缺陷」还是「测试缺陷」

**现象**：N1 冒烟首跑 21/23，两条 FAIL 的**性质完全不同**：

| FAIL | 真实性质 | 处置 |
|---|---|---|
| `Origin: https://127.0.0.1:8795` 被**放行** | **产品缺陷** —— `_guard()` 只校验 Origin 的 host，未校验 scheme 与端口 | 收紧产品：要求 scheme=`http`、host 白名单、port=实际绑定端口 |
| 落盘目录被报"缺失" | **测试缺陷** —— 断言用 `TARGET.rglob()` 拿到的是**绝对路径**，却与相对路径期望值比较 | 修测试：改用 `p.relative_to(SANDBOX).as_posix()` 作基准 |

**教训**：看到 FAIL 先判断"**是产品错了，还是测试错了**"。一律改产品会把正确的实现改坏；一律改测试会放过真缺陷。两条都要留证据（用了哪组输入、期望什么、实际什么）。

**再犯一次（2026-10-09，P0-1 写 `tests/test_dtree_core.py`）**：新写的两条断言一跑就红 ——

| FAIL | 真实性质 | 处置 |
|---|---|---|
| `count_tree({a:{b:{},c:{d:{}}},e.md,f.txt})` 期望 `(3,2)`、实得 `(4,2)` | **测试缺陷** —— 漏数了 `a` 本身（`a`、`a/b`、`a/c`、`a/c/d` 共 4 个目录） | 改期望为 `(4,2)` |
| `dry_run=True` 时期望 `createdDirs == []`、实得计划项 | **测试缺陷** —— 既有契约规定 dryRun **同样返回 planned 结构**（前端要用它显示"演练完成：目录 N"） | 改期望为「只断言 `createdDirs` 长度 == 目录数」 |

**补充判据**：写断言前**先读实现的既有契约**（含函数的返回约定），不要凭函数名推断语义。"我以为是空"不等于"契约是空"。

### 11. 监听回环 ≠ 只有本机能调用

**现象**：服务绑定 `127.0.0.1` 即被视为"安全"，但实测（2026-10-09）`app.py` **全文无任何来源校验**，`do_POST` 仅比对路径。
**后果**：本地任意网页、乃至公网页面经 **DNS rebinding**，都可盲发 `POST /api/generate` 触发磁盘写入。关键认知 —— **CORS 只限制「跨域读取响应」，无法阻止「跨域发起请求」**（简单请求不预检，读不到响应但副作用已发生）。
**规范**：见 `docs/项目约定.md` §P0-5 —— Host 白名单 + Origin 严格同源（scheme/host/port）+ 写操作防护头 `X-QingMan` + 拒答 CORS 预检。
**验证**：沙盒冒烟 25 项，其中「被拒请求均未落盘」单独断言。

### 12. 无头截图必须等样式应用完成

**现象**（2026-10-09，V0.0.3）：用无头 Edge `--screenshot` 验证深色主题，首轮图片显示「背景仍是浅色」，据此一度怀疑 CSS `mask` 或主题变量没生效。

**真相**：页面本身完全正确 —— 探针页读 `getComputedStyle` 得到 `body.background: rgb(22, 26, 31)`、`logo.background: rgb(125, 214, 176)`、`mask-image` 指向 `assets/logo.svg`，全部符合预期。问题出在**抓帧时机**：未加 `--virtual-time-budget` 时，无头浏览器可能在样式完全应用前就截图。

**正确做法**
- 截图命令固定带 `--virtual-time-budget=3000~5000`，并用**独立的 `--user-data-dir`**（避免复用已锁定的 profile 目录而静默失败）
- **判断样式是否正确以计算样式为准**（`getComputedStyle` 探针页），截图只用于确认真实观感
- 探针页模板：加载 CSS 后用 JS 把 `--qm-*` 变量值、`body`/目标元素的 `backgroundColor`、`mask-image`、盒子尺寸打印到页面上再截图 —— 一次拿到全部客观值

**教训**：若按首轮截图下结论，会误判为「mask 方案不可用」并错误回退到内联方案。

### 13. 不可从位图反推矢量源文件结构

**现象**（2026-10-09，V0.0.3 开工前）：仅凭两张 PNG 就断言「`_02_01_01.png` 是源 SVG 的位图导出、`_02_01_02.png` 没有对应 SVG」「SVG 只有 2 个 path、纯黑」。读到源文件后**两处全部推翻**：

- `inkscape:export-filename` 指向的是 **02**，两张 PNG 实为**同一 SVG 的两次导出**
- 源文件实为**两图层三元素**：一个白色圆角底板 `rect` + 一个 `fill:none` 的**不可见** `path`（与可见 path 同形 1748 点）+ 可见 `path`

**规则**：面对设计源文件，**必须逐元素读取实际内容**（图层结构、每个元素的 `style`、`viewBox`、`inkscape:export-*` 元数据），不得从导出物反推。**位图只能证明它自己的像素**。

**附带教训**：源文件里的元素数 ≠ 可见元素数。`fill:none` 且无 `stroke` 的路径是彻底的冗余，直接用于交付会带上无意义的体积与误导性结构。

### 14. `.brand-logo` 依赖父容器为 flex

`.brand-logo` 只声明了 `width` / `height`，**没有声明 `display`** —— 在非 flex 容器中（如普通 `<div>`），它是 inline 元素，宽高不生效，会**塌陷成 0 而完全不可见**。

**实测**（2026-10-09，V0.0.3）：做尺寸可读性对照页时，把标记直接放进普通 `<div>` 做 8 倍放大展示，结果三个放大框**全空**；而同一份 CSS 在页面上方 flex 布局的尺寸行里（`.cell` 为 flex column）显示完全正常。

**约定**：`.brand-logo` 必须在 **flex 容器**内使用 —— 现有两处 `.brand` 均为 `display: flex`，满足前提。若今后要在非 flex 场景复用（如独立图标页、邮件模板），**须先补 `display: block`**；那时属 `src/` 改动，需升版或追加同版本修订。

**推广**：凡只给尺寸、不给 `display` 的组件类，都要写明「依赖 flex 父容器」这个前提。

### 15. `write_text` 的默认换行会因平台改变字节

`Path.write_text(s)` **不传 `newline=`** 时等价于 `newline=None` —— 写出时把 `\n` 统一译为 `os.linesep`。Windows 上 `os.linesep == '\r\n'`，于是**同一段代码在 Windows 与 Linux 会写出不同字节**。

**实测**（2026-10-09，清点 `preview/` 时发现）：

| 写法 | 盘上字节 |
|---|---|
| `p.write_text("V0.0.3" + "\n", encoding="utf-8")` | `b'V0.0.3\r\n'` ← Windows 实际行为 |
| `p.write_text(..., encoding="utf-8", newline="\n")` | `b'V0.0.3\n'` |

**为什么在本项目是硬伤**：项目用 **SHA-256 指纹**校验内容，且 `.gitattributes` 设 `* -text` **禁止任何换行转换**。字节一变指纹即失配 —— `verify.py --against` 会直接判不通过。

**全项目扫描结果**

| 位置 | 判定 |
|---|---|
| `tools/release.py:45` 写 `VERSION` | 🔴 **有害**（bump 后 `VERSION` 变 CRLF） |
| `tools/promote.py:112` 写主线 `VERSION` | 🔴 **有害**（落地后 `VERSION` 变 CRLF） |
| `tools/verify.py:227` 写临时 `.mjs` | ⚪ 无害（临时目录，不落项目） |
| `tools/store.py:229` 写 `MANIFEST.json` | ⚪ 无害（指纹对**文件映射**算，非清单自身字节） |
| `tools/handoff.py:186-188` | ✅ **正确范例**（`open(..., newline="\n")`） |

**易踩的兼容坑**：`write_text` 的 `newline` 参数**Python 3.10 才有**，而本项目下限 **3.8** —— 修法必须走 `open(..., encoding="utf-8", newline="\n")`（`handoff.py` 已这么做，且注释写明原因）。

**另一面（好消息）**：`store.py` 的恢复路径用 `write_bytes`（:196）与 `shutil.copy2`（:308），**逐字节**，故 `checkout` 取回的内容**绝不会被转换** —— 这也是「删掉 `preview/` 仍能完整取回」的技术前提。

**约定**：项目内所有**文本写入**必须显式声明换行，统一 `newline="\n"`；确需 CRLF 的文件（如 `start.bat`）须显式写 `\r\n` 并在约定中单列。

**实例补充（2026-10-09 修复当日）**：`verify.py` 加入「换行一致性」检查后**立即**报出 `src/web/assets/logo.svg` 含 CR —— 它是 V0.0.3 落盘时由**沙盒生成脚本**（同样裸用 `write_text`）产出的。这说明陷阱不只在自己人的工具里，**"临时生成脚本"同样在射程内**。凡生成文本交给项目的脚本，一律照 `newline="\n"` 写。

**尚存同类点（属 `src/` 产品行为）→ 已于 V0.0.4 一并处理（2026-10-09）**

| 位置 | 原状 | 处置 |
|---|---|---|
| `src/server/routes.py:112` 写 `data/editor.json` | 裸 `tmp.open("w")` → Windows 下 CRLF | 改 `open(..., encoding="utf-8", newline="\n")`。该文件不入 git、不进版本清单，此改动**纯为消除平台漂移**，无用户可见影响 |
| `src/server/dtree_core.py:194` 写**生成的目录树文件** | 同上 → **用户产出文件在 Windows 下是 CRLF、在 Linux 下是 LF** | 改 `open(..., encoding="utf-8", newline="\n")` |

**为什么 `dtree_core.py:194` 是「真缺陷」而不只是洁癖**：它写的不是项目自己的文件，而是**用户在磁盘上拿到的产出**。同一棵树在两台不同系统的机器上生成，字节不同 —— 这本身即"不可复现"。修掉之后产出**只由输入决定，不由平台决定**。

**顺带修掉的一个真缺陷**：`routes.py` 的 `save_editor()` 原先返回的 `bytes` 取自**写入前的字符串长度**，而盘上文件在 Windows 下是 CRLF、比它长。响应里的 `bytes` 因此**小于实际文件大小**。改用 `open(..., newline="\n")` 后两者一致，单元测试（`tests/test_routes.py`）专门断言了这一点。

**遗留未决（见 §三.19）**：`newline="\n"` 是**全局**策略 —— 若将来模板里出现 `.bat` / `.cmd` / `.ps1` 节点，LF 会让 `cmd.exe` 的多行解析（`goto` 标签、括号块）出问题。当前 17 套模板的文本文件只有 `说明文档.md`（均 + `.txt` 若干），**尚不触发**。

### 16. `bytes` 字面量只能含 ASCII

**现象**（2026-10-09，P0-2 写 `tools/smoke.py`）：为测「非法 JSON」分支，写了 `b"{不是 json"` → `SyntaxError: bytes can only contain ASCII literal characters`。

**原因**：`b"..."` 是**字节**字面量，源码里只允许 ASCII 字符；中文属非 ASCII，即使在字符串里合法也不能直接写进 `b""`。

**正确写法**：先写 `str` 再编码 —— `"{不是 json".encode("utf-8")`。

**推及**：凡要发非 ASCII 字节（中文请求体、中文文件名）给 `http.client` / `socket` / 文件，一律走 `.encode("utf-8")`。

### 19. 生成文件的换行：全局 LF 与 `.bat` 的边界（遗留未决）

`dtree_core.py` 生成文件时统一用 `newline="\n"`（见 §三.15 修订），这对 `.md` / `.txt` / 无后缀的文本**完全正确**：确定性、跨平台一致、且现代 Windows 编辑器（记事本 Win10 1809+、VS Code）都正常显示。

**但 `.bat` / `.cmd` / `.ps1` 是例外**：`cmd.exe` 对 LF-only 的批处理在**多行结构**（`goto :label`、`( ... )` 括号块、`if ... else` 跨行）下可能解析异常。它们是 **Windows 唯一认可 CRLF 的文本类型**，也正是本项目自身 `.gitattributes` 给 `start.bat` 定 CRLF 的原因。

**当前是否触发**：**否**。17 套模板里的文本节点只有 `说明文档.md`（外加若干 `.txt`），文件名的换行敏感后缀**暂未出现**。但用户在界面上**可以自己新建**名为 `启动.bat` 的节点 —— 那时就是真问题。

**候选方案（未实施，属 `src/` 改动 → 需升版）**：按**扩展名**决定换行 ——

| 扩展名 | 换行 | 依据 |
|---|---|---|
| `.bat` / `.cmd` / `.ps1` | `\r\n` | Windows 唯一认可的批处理换行 |
| 其余（含无后缀） | `\n` | 确定性 + 跨平台一致 |

**关键设计原则**：判据必须是**扩展名**，**不能是 `os.linesep`** —— 后者会把"平台差异"重新引入产出（正是 §三.15 要消灭的东西）。按扩展名是**规则确定**的，同一输入在任何平台产出同一字节。

### 21. `git rm` 会拒绝删除「只有新增暂存」的文件 —— 须 `-f`

**现象**（2026-10-09，清空 `preview/V0.0.6/`）：

```
error: the following files have changes staged in the index:
    preview/V0.0.6/VERSION
    ...（29 个）
(use --cached to keep the file, or -f to force removal)
```

**原因**：这些文件是**新加入索引**（`A`）而**从未提交**；`git rm` 默认拒删"索引与 HEAD 不一致"的条目，属安全护栏。

**git 层面的解法**（仅在"该条目**确已被跟踪 / 已暂存**"时适用）：`git rm -r -f <目录>`。此处的 `-f` **不构成数据丢失风险** —— 内容已由 `store.py commit` 固化在对象池，且主线已是同内容。
> ⚠️ **但"先 `git add` 再 `git rm -r -f`"不是清空 `preview/V<版本>/` 的正确路线** —— 见下方【更正】。

**它牵出的问题（一度以为规则冲突）**：`docs/项目约定.md` §P1-7 的 R1 / R2 / R5 看着打架 —— R1「`promote` 后即清空」、R2「删除统一走 `git rm -r`」、R5「`preview/` 保留在 git 跟踪内」。

**【更正 2026-10-09，沙箱实证】三者从来不冲突 —— 是我把 R2 的适用面放宽了。**

R2 只管「**已被 git 跟踪**的内容」的删除。§P1-7 生效后 preview 副本**本就不该进索引**，于是 R2 对**常态根本不适用**；R1 与 R5 各管自己的事（前者管"何时清"，后者管"目录与占位文件留在跟踪内"）。所谓"三条表面冲突"**是误判**。

**而"先 `git add` 再 `git rm -r -f`"这个处置是错的** —— 我据它写进 §P1-7 的「规则细化」**已作废**。沙箱最小仓库（`_sandbox/gitrm_probe_20261009/`）实证：
1. `git add` → `git rm -r`（无 `-f`）**被拒**（复现本坑）；加 `-f` 后 `git diff --cached` 为空、`git status` 干净 → **净效果为零**：`git add` 除"让 `git rm` 可用"外**毫无作用**。
2. **若 `git add` 后忘了 `git rm` 就直接提交 → `preview/V<版本>/` 真的进入历史**（`git ls-tree -r HEAD` 可见）→ **这套做法会制造它本想避免的结果**（违反 R1 本意）。
3. **正确路线**：**不进索引** —— `git clean -nd preview/V<版本>` 演练 → `git clean -fd preview/V<版本>`；索引不受影响、`git status` 干净，被跟踪的 `preview/README.md` 与目录本身均保留（R5 成立）。

**正确规则（已更正 §P1-7「清空细则」）**：先跑 `git ls-files preview/V<版本>` —— **非空**（副本已被跟踪，历史遗留）→ `git rm -r`；**为空**（从未进索引，§P1-7 生效后的常态）→ **不要 `git add`**，用 `git clean -fd`。两条路都须先备齐三项证据（sha256 逐字节一致 / blob 在对象池 / 可取回）。

**通用教训（已修正）**：遇到"规则之间看着打架"，先分辨是**真冲突**，还是**自己把某条规则的适用面放宽了**。本例属后者 —— 我把 R2 当成了"一切删除都必须走 `git rm`"。**先核准适用面，再谈操作顺序。**

### 23. 「记忆型」UI 状态不能按"用户正在编辑的字段"动态推断

**现象（设计阶段拦下，未上线）**：生成参数区要可折叠。最自然的写法是**不存偏好**，每次渲染时推断：

```js
function genBarCollapsed() {
  return !!el('inTarget').value.trim();   // 目标位置已填 → 收起
}
```

**后果**：用户在展开状态下**输入目标位置的第一个字符**，`input` 事件触发重绘 → 判定瞬间变为"已填" → **参数区自动收起**，把用户正在操作的输入框藏起来。而帮助页的引导顺序恰恰是"先填目标位置"（`help.quickStart.4`）。

**根因**：判定条件与**用户此刻正在编辑的字段**耦合，导致"用户一开始输入，状态就翻转"——自相矛盾。

**正解**：**这种"记忆型"状态只在启动时定一次并落盘**，之后完全由用户主动切换控制：

```js
function initGenBar() {
  if (!getGenBarState()) setGenBarState('open');   // 首次展开
  renderGenBar();
}
```

**通用教训**：状态推断的**输入**里，不要包含"用户此刻正在改的那个东西"。判断依据要么取**已提交/已保存**的值，要么**只算一次**。

**已固化为验收**：注入式行为探针把这条写成断言 `输入过程不会自动收起/展开`，以后改动若破坏它会立刻变红。

### 26. 给 `§` 引用加守卫时，中文散文会被误判成编号

**现象**（2026-10-09，实施「源码 § 引用可解析」守卫时，**实证抓出**）：首版标签正则是 `§\s*([A-Za-z0-9]+…|[\u4e00-\u9fff]+)`。在沙箱探针（`_sandbox/srcref_probe_20261009/`）里，文档串 `"""沙箱探针 · 源码 § 引用守卫反向验证。` 中的**散文**「§ 引用守卫反向验证」被当成标签 `引用守卫反向验证`，报出**误报**：

**通用教训**：**给"符号 + 标识符"写正则时，先定清楚"什么不算引用"**。符号在自然语言里常有非引用用法（此处 `§` 可作"章节"讲），若不在模式里排除，守卫就会**惩罚正常写作** —— 而一个会误报的守卫，最终结局是被绕过。**排除规则本身也要写进文档**（本轮已写入 `verify.py` 代码注释与 §三.22 的「防复发」段）。

### 27. 拿"没核实的假设"去写裁定依据：帮助页说"键位待定"，代码里早有 `Ctrl+S`

**现象**（2026-10-09，V0.0.7：处理 §P2 第 8 项「快捷键约定」时**自查发现**）：我先给出的裁定建议写着「产品为**全鼠标驱动**、无任何全局键盘监听」。落到盘上一查 —— **`src/web/js/main.js:364-370` 早已有 `Ctrl / Cmd + S` 立即保存**（`keydown` + `preventDefault()` + `saveNow()`）。

真正的问题因此**完全反转**：不是"要不要设快捷键"，而是**键位已经存在、帮助页却没写**
（`help.kbd.pending` = 「功能面尚未稳定，键位约定待定，本表暂留空」）—— 这是**文档与实况不符**，而非"待约定"。

**原因**：我把"帮助页留空占位"当成了"没有键位"的证据。**占位文案描述的是"约定未定"，不等于"功能不存在"**；两者之间没有蕴含关系，我却当成了等价。

**处置**：裁定与实施都按实况重写 —— 帮助页**补登** `Ctrl / Cmd + S`（新增取词键 `help.kbd.save`），`help.kbd.pending` 改为「本版仅设上述一项」。§P2 第 8 项条目内**显式标注「原假设经核查不成立」**。

**通用教训**：**"某功能没被文档描述" ≠ "该功能不存在"**。凡在建议/裁定里写"产品**没有** X"，都必须先跑一次反向检索（`grep` 关键词 / 监听器 / 取词键）**证明其不存在**，而不是用"文档里没提"来推定。本项目的 `verify.py` 只能校验"该有的有没有"，**查不出"我声称没有的其实有"** —— 这类错误只能靠人工核实。

### 28. 判据写进文档却**恒为假**：「看该行首是否带 ✅」

**现象**（2026-10-09，V0.0.7）：上一轮把 §P2 改名时，我写下一条判据「**看该行首是否带 ✅**」。本轮执行时发现它**永远为假** —— §P2 是 Markdown 表格，行首恒为 `| 编号 |`，`✅` 全部落在**第 3 列（说明列）之内**。

**危害**：判据是给人（和后续 AI）看的操作说明。一条恒假的判据会让"已结案 / 待决"的分类**完全无法执行**，而表面上它读起来还挺合理。

**处置**：判据改为「看**说明列开头**是否含 **✅**（已结案）／**⚠️**（挂起）；两者皆无即待决」，并在文档里**保留被更正的原文**（划掉 + 说明为何错），而不是悄悄改掉。

**通用教训**：**写"判据 / 检查动作"时必须当场对着真实数据跑一遍**。本项目 §P2 表当时已有 4 行带 ✅，只要随手点开看一眼就能发现判据不成立 —— "看起来对"和"跑一遍对"之间的差距，正是这类文档型错误的全部来源。**判据也是一种"承诺"，同样要有验收**（呼应 §一.7「无实现、无验收的条目不得写入」）。

**【同轮复发，已实测】**：修正判据后，我**立刻又踩了同一个坑**。按新判据（"看**说明列开头**是否含 ✅ / ⚠️"）逐行核对，15 项里有 **4 项判不出来**：

| 项 | 问题 |
|---|---|
| 第 **12 / 13** 项 | 内容已写明"已实施 / 已修复"，**却忘了加 ✅ 前缀**（格式没跟上结论） |
| 第 **11** 项 | `✅` 写在说明列**中间**（"…**✅ 处置结果（2026-10-09 已完成）**"），不在开头 |
| 第 **15** 项 | 用文字"**已裁定并实施**"**代替了符号**，根本没有 ✅ |

**修正**：统一把 `✅` / `⚠️` / `⏳` 放到**说明列开头**（后接简述）。**修正后核验：13 结案 ／ 1 挂起 ／ 1 待决，15 项全部可判定。**

**延伸教训**：**新定的格式规范，必须立刻回头把已有数据全部套一遍**。否则规范只对"从此往后的新条目"生效，老条目继续不合规，判据照样失效 —— 这与"只给新代码加测试、老代码不管"是同一类问题。

### 29. 同一份数据两种口径：字节求和 137K vs `du` 磁盘块 180K

**现象**（2026-10-09，V0.0.7：为 §P2 第 4 项「体积上限」定基线时发现）：我先前写下的基线是「`src/` 合计 **180 KB**」（取自 `du -sh src/`），而本轮写进 `verify.py` 的体积断言按 `st_size` **求和**算出的是 **137 KB**。两者相差 43K。

**原因**：`du` 报的是**磁盘占用**（按文件系统簇对齐，本项目小文件多，每个文件至少占一簇）；`st_size` 求和报的是**逻辑字节数**。二者对同一目录**都正确**，只是口径不同。

**处置**：文档统一采用**与断言一致的口径**（字节求和 = **137 KB**），并**显式注明** `du` 口径为 180K、差异来自簇对齐 —— 避免下次有人用 `du` 复核时以为断言算错。

**通用教训**：**凡是会被工具复算的数字，文档里必须写明口径**（字节 / 磁盘块、含不含子目录、压缩前 / 后）。写"约 180K"而断言算 137K，会让人怀疑断言本身有 bug，白耗一轮排查。**数字的可复现性，取决于口径是否一起写下来**。

### 30. 「本表暂留空」是一句会被代码沉默推翻的断言 —— 它潜伏了 5 个版本

**现象**（2026-10-09，V0.0.7）：帮助页「快捷键」小节自建立起就写「功能面尚未稳定，键位约定待定，本表暂留空」（`help.kbd.pending`）。而在 §P2 第 8 项收口时核对发现，产品**早就有 `Ctrl / Cmd + S` 立即保存** —— `src/web/js/main.js:365-370`（`keydown` + `preventDefault()` + `saveNow()` 跳过防抖）。

**时间线（git 实测）**：

| 提交 | 内容 | 该文案是否成立 |
|---|---|---|
| `fbea984`（提交序 #8） | 帮助页独立成页，写下「本表暂留空」 | **成立** —— 当时产品确实零快捷键 |
| `27770c3`（#12，V0.0.2） | 加入 `Ctrl / Cmd + S` | **从这一刻起即为假** |
| V0.0.3 / V0.0.4 / V0.0.5 / V0.0.6 | —— | 一直为假，**无人发现** |

**性质**：这不是"写错了"。那句文案在下笔时**准确且合理**，问题在于它是一句**与代码耦合、却无人看守的断言**：只要有人新增一个快捷键，它就自动变假，而**代码侧没有任何东西提醒文档侧**。它潜伏 5 个版本、跨 4 次交付校验都没被抓到。

**为什么必须告知（这不只是"写不写"的取舍）**：`main.js:367` 有 `preventDefault()` —— 该键**抢占了浏览器自带的 Ctrl+S「保存网页」**。用户按下去会被产品接管、不会弹出保存网页对话框。帮助页若仍说"本表暂留空"，用户**永远不知道这个键已被占用**。

**处置**：① 帮助页登记该项（新增取词键 `help.kbd.save`）；② `help.kbd.pending` 语义由"待约定"改为"**本版仅设上述一项**，其余待功能面稳定后统一约定"；③ 新增机器守卫 `verify.py` 第 **7g** 项 —— **源码出现修饰键监听（`ctrlKey` / `metaKey` / `altKey`）时，帮助页键位小节必须登记至少一条具体键位**，只留 `help.kbd.pending` 占位即判不通过。四分支沙箱实证：只留占位 → FAIL（并打印源码命中位置）；补齐登记 → PASS；源码无修饰键监听 → 跳过 PASS；键位小节整段缺失 → FAIL。

**通用教训**：**写进文档的"否定性断言"（"没有 X"、"暂留空"、"待定"）必须有人守**。肯定性断言写错了，使用中迟早暴露；**否定性断言写错了没人会察觉** —— 因为"这里什么都没有"看起来永远正常。给这类断言配一个**机器守卫**（本例：源码有键位 → 文档必须有登记，反向不成立），是唯一可靠的解法（与 §三.27 同源）。

| 关 | 做法 | 看什么 |
|---|---|---|
| **行为探针** | 向副本页注入一段脚本，用 `click()` / `dispatchEvent()` 驱动控件，把断言结果画成 `#__dump` 覆盖层 | 状态切换、`aria-*`、`localStorage` 落盘、**"不该发生的自动变化没发生"**（如 §三.23） |
| **WCAG 对比度审计** | 同样注入式：遍历 `body *`，沿祖先链取**不透明**背景，算 `(L1+0.05)/(L2+0.05)` | 新增文本是否引入**新**违规（深色截图须 `--force-dark-mode` **加** `--disable-features=WebContentsForceDark`，见 §三.20） |

两者都用无头 Edge 截图读取结果 —— 注意**逐张用独立 `--user-data-dir`**，否则 `localStorage` 会从上一次运行带过来，让"初始态"断言失真。

**核验纪律**：任何"生成类"命令（截图、导出、工具产出）**不能只看 exit code**，必须再验一次**文件真实存在且非零大小** —— 本项目实测过 exit code 全 0 而产出 0 个的案例（§三.17）。
